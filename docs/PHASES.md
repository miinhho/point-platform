# 작업 단계

`JOURNEY.md` 가 무엇을 만들지 정하고, 이 문서는 어떤 순서로 만들지 정한다.

단계는 **여정의 순간 순서**를 따른다. 기술 레이어별로 쪼개면 어느 순간도 끝까지 완성되지 않은 상태가 오래 유지되고, 그러면 "이 순간에 사용자가 막히는가"를 확인할 수 없다.

| Phase | 여정 | 내용 | 필요 환경 | 상태 |
|---|---|---|---|---|
| 0 | — | 기반: 계약 · 도메인 · Mock · Expo 셸 | 없음 | **완료** |
| 1 | — | 플로우 상태 기계 | 없음 | **완료** |
| 2 | — | 디자인 시스템 · 화면 전환 | 브라우저 | **완료** |

| 4 | 4 | 보낼지 결정한다 (확정 화면 · 홀드) | 브라우저 | **완료** |

Phase 3~6 은 브라우저에서 완결된다. UI 본체가 WebView 안의 웹 앱이라서, 셸을 나중에 붙여도 앞의 작업이 헛되지 않는다.

다만 "브라우저에서 완결"은 논리의 이야기다. 손의 문제(터치 크기·도달 범위·체감 속도)는
Phase 7 을 기다리지 않고 폰 Chrome 으로 매 Phase 확인한다 — 운영법은 `FIELD.md`.

## Phase 1 — 플로우 상태 기계 (완료)

화면 전환을 라우터가 아니라 상태 기계로 다룬다. 여정 5 가 요구하기 때문이다 — 시스템 back 의 의미가 순간마다 달라야 하고("보내는 중에는 아무것도 하지 않는다"), 라우터의 history pop 에 맡기면 그 규칙을 표현할 수 없다.

- `web/src/flow/transferFlow.ts` 상태 · 액션 · 리듀서
- `resolveBack()` — `action`(되돌린다) / `ignore`(소비하되 아무것도 안 한다) / `exit`(셸에 넘긴다)

검증 33케이스 통과. 특히 `sending` 전체 구간에서 back 이 `ignore` 이고, 실패 후 재시도가 같은 멱등성 키를 재사용한다.

## Phase 2 — 디자인 시스템 · 화면 전환 (완료)

두 가지가 빠져 있었다. 시각 언어의 기준이 없어서 화면마다 스타일을 새로 쓰고 있었고,
화면 전환이 없어서 어디서 어디로 왔는지 알 수 없었다.

- **Chakra UI v3** 로 전환. 자체 emotion 토큰(`ui/theme.ts`)을 버렸다 — 값에 근거가 없었고,
  검증된 스케일을 임의값으로 대체할 이유가 없다. `@emotion/styled` 의존성도 함께 제거
- `web/src/ui/system.ts` — `gutter` 간격 토큰, `issue`·`pending` 시맨틱 색, 금액·이름·핸들
  textStyles, WebView 흔적을 지우는 globalCss
- 색 모드 `자동 / 밝게 / 어둡게` 3택 (`ui/ColorModeSelect.tsx`). 2택 토글이면 한 번 누른
  사용자가 시스템 따르기로 돌아갈 방법을 잃는다
- **화면 전환** (`ui/ScreenTransition.tsx` · `ui/screenDepth.ts`) — 여정의 순간마다 깊이를
  정해두고, 깊이가 커지면 오른쪽에서 들어오고 작아지면 왼쪽에서 들어온다. 나가는 화면은
  30%만 밀린다 (떠나는 것이 아니라 가려지는 것이다)
- `ui/motion.ts` — Chakra 스타일 프롭과 motion 제스처를 한 요소에서 쓰기 위한 어댑터.
  `transition` 은 이름이 겹치므로 넘기지 않는다 (`<Box asChild>` 로 감싼다)

검증 (브라우저 390×844)
- 전진 시 새 화면이 오른쪽에서, 후진 시 왼쪽에서 들어오는 것을 캡처로 확인
- `prefers-reduced-motion` 에서 위치 이동이 사라지고 교차 페이드만 남는다.
  이때는 `AnimatePresence` 를 `wait` 로 바꾼다 — 이동이 없으면 겹친 두 화면의 글자를
  구분할 단서가 없어서, 하나가 사라진 뒤에 다음이 나타나야 한다
- 자동/밝게/어둡게 3택이 모두 적용되고, 선택 표시가 칸 사이를 미끄러진다

남은 것: 60fps 실측은 Phase 8 (실기기)에서 한다. 브라우저 추정치는 쓰지 않는다.

- `ui/useSystemBack.ts` — 웹에서 시스템 back 을 상태 기계에 연결한다 (아래)
- `ui/amountFit.ts` — 자릿수에 맞춰 금액 글자 크기를 줄인다 (아래)

### 동명이인을 다루는 세 겹

원장에 김지수가 두 명 있는 것은 이 위험을 재현하기 위한 것이다. 한 겹으로는 부족했다.

1. **붙여 놓는다** (`groupHomonyms`) — 최근순 정렬을 유지하되 같은 이름을 첫 등장 자리로
   끌어온다. 목록 1번과 9번에 떨어져 있으면 사용자는 둘이 있다는 사실 자체를 모른다
2. **핸들을 올린다** — 겹칠 때만 본문 대비·본문 크기로. 항상 크게 두면 배경이 되어
   정작 겹치는 순간에 눈에 띄지 않는다
3. **묶음에만 안내를 붙인다** — "같은 이름 2명 · 핸들로 구분한다". 화면 상단 배너로
   띄웠다가 물렸다. 목록에 들어갈 때마다 보이는 경고는 곧 읽히지 않는다

### 만 키를 넣은 이유

"삼만"을 옮기는 데 `3·0·0·0·0` 다섯 번을 누르게 하면 누르는 동안 자릿수를 세어야 한다.
그 세는 일이 바로 자릿수 오타가 생기는 자리다. 한국어 금액은 만 단위로 말해진다.

상한을 넘을 때 **일부만 붙이지 않는다.** 3만을 누르려다 조용히 3천이 되면, 자릿수 오타를
막으려고 만든 키가 자릿수 오타를 만든다.

### 실기기 검증이 잡아낸 것 (R1)

실기기 세션이 두 가지를 되돌려 주었고, 둘 다 브라우저에서는 보이지 않았다.

**시스템 back 이 앱을 떠났다.** "웹이니까 당연"이지만, `App.tsx` 의 주석은 "웹에서는
브라우저 뒤로가기가 이 함수를 부른다"고 써 있었는데 `popstate` 를 듣는 곳이 없었다.
`resolveBack` 은 이 앱의 핵심 판단인데 **웹에서 그것을 부르는 경로가 하나도 없었다** —
테스트에서만 맞는 코드였다. `ui/useSystemBack.ts` 가 히스토리에 덫을 하나 놓아
연결한다. 화면이 히스토리에 쌓이지 않으므로 라우터가 아니고, back 의 의미는 여전히
`resolveBack` 혼자 정한다. Phase 7 에서 `BackHandler` 를 붙일 때 이 덫과 겹치지 않게
해야 한다.

**실기기 CSS 뷰포트가 360×780 이었다.** 내 브라우저 검증은 390×844 였다. 360 에서
13자리를 넣으니 금액과 한글이 오른쪽에서 잘렸다 — 자릿수 오타를 막으려고 만든 화면이
자릿수를 감추고 있었다. `ui/amountFit.ts` 가 자릿수에 따라 글자를 세 단계로 줄인다.
실제 폭을 재지 않는 것은, 측정이 렌더 후에야 가능해서 한 프레임 동안 잘린 상태가
보이고 그 한 프레임이 하필 사용자가 금액을 확인하는 순간이기 때문이다.

전환 스프링도 "살짝 느리다"는 관찰에 따라 `520 / 44 / 0.8` 로 올렸다 (R2 에서 재판단).

### 검증

`npm test` — 103케이스. Phase 4~6 에서 실패 설명 7 · 취소 창 4 · 비율 표기 6 · 내역 상태 3 · **back 조합 2** 가 늘었다.
문서가 인용하던 테스트가 저장소에 없어서 vitest 로 다시 세웠다. 돌릴 수 없는 검증은
검증이 아니다.

**탭 횟수 실측** (홈 → 확정 화면 도달, 브라우저 390×844)

| 금액 | 경로 | 탭 |
|---|---|---|
| 3만 | 최근 대상 → `3` → `만` → 확인 | **4** |
| 30만 | 최근 대상 → `3` `0` → `만` → 확인 | 5 |
| 100만 | 최근 대상 → `1` `0` `0` → `만` → 확인 | 6 |
| 3만 (검색 경유) | 보내기 → 검색 → 대상 → `3` → `만` → 확인 | 5 + 입력 |

목표(4회 이하)는 **만 단위 한 자리 금액에서만** 달성된다. 30만·100만은 5~6회다.
프리셋 칩이나 "최근 보낸 금액"으로 줄일 수 있지만, 근거가 될 이력 데이터가 아직 없어서
넣지 않았다. 실기기 검증에서 이 횟수가 실제로 부담인지 먼저 본다 (`FIELD.md` R2).

그 외
- 150만/1500만이 "백오십만"/"천오백만"으로 갈라진다 (`points.test.ts`)
- 같은 이름 두 명이 화면에 나란히 들어온다
- 잔액을 넘으면 금액과 한글이 함께 붉어지고 확인 버튼이 잠긴다. 버튼을 감추지는
  않는다 — 자리가 사라지면 다음에 무엇을 해야 하는지 알 수 없게 된다

## Phase 4 — 여정 4: 보낼지 결정한다 (완료)

- `screens/Confirm.tsx` — 보낸 뒤의 세계 전부. 받는 사람 / 금액 / 지금 잔액 / **보낸 뒤 남는 잔액**
- `ui/HoldButton.tsx` — 홀드 확정. 포인터·키보드(스페이스) 양쪽
- `flow/useFlowRunner.ts` — 리듀서와 서버 사이. API 호출을 화면에서 걷어냈다

**남는 잔액이 여기 있는 이유.** 사용자가 확인하려는 것은 금액 자체가 아니라 "이걸 보내도
괜찮은가"다. 그 판단에 필요한 값을 화면이 대신 계산해 주지 않으면 사용자가 머릿속에서
뺄셈을 해야 하고, 그 뺄셈은 틀린다.

**홀드 버튼의 색.** 차오르는 면 위로 글자가 지나가는데, 처음엔 연한 바탕에 진한 글자로
만들었더니 채워지는 도중 글자가 읽히지 않았다. 바탕을 실색으로 두고 차오르는 면은 그것을
어둡게 덮게 바꿨다. 두 배경 모두에서 같은 글자색이 읽힌다.

검증 (브라우저)
- 확인 다이얼로그 **0개**
- 300ms 시점 `scaleX 0.49` — 차오름이 선형이고 남은 시간과 일치한다
- 200ms 만에 손을 떼면 발동하지 않는다. 끝까지 누르면 `sending` 으로 간다

## Phase 5 — 여정 5~6: 보내는 중 · 끝났다 · 실패했다 (완료)

- `screens/Sending.tsx` — 취소 창과 처리 중을 **다른 화면**으로 다룬다
- `screens/Done.tsx` · `screens/Failed.tsx`
- `domain/failures.ts` — 실패 코드를 "무엇이/돈이 어디에/뭘 할 수 있는지"로 옮긴다
- `ui/DevPanel.tsx` — 지연·실패·단계 속도 주입, 역할 전환, 원장 리셋

**취소 창에서 "보내는 중"이라고 쓰지 않는다.** 서버는 아직 아무것도 하지 않았다.
화면은 **"3초 후 보냅니다"** 라고 쓰고, "지금 취소하면 잔액은 그대로다"라고 덧붙인다.
취소할 수 있다고 말하면서 이미 출금해 두는 것도 거짓말이고, 아무것도 안 했으면서
보내는 중이라고 하는 것도 거짓말이다.

**결과를 알 수 없는 실패는 단정하지 않는다.** `NETWORK`·`SERVER` 는 서버가 요청을
받았는지 알 수 없다. 화면은 "실패했습니다" 대신 "서버가 요청을 받았는지 알 수 없다.
다시 시도해도 두 번 처리되지 않는다 — 같은 요청으로 취급된다"라고 쓴다. 그 문장이
참인 이유는 멱등성 키뿐이다.

검증 (브라우저, 단계 각 2초로 늦춰서 초 단위 기록)

```
1s  취소 창 · "2초 후 보냅니다" · 취소 버튼 있음
3s  처리 시작 · 취소 버튼 사라짐 · 완료 단계 0개
5s  ✓ 출금        7s  ✓ 요청        9s  ✓ 검증        11s ✓ 입금
12s 완료 · 잔액 3,240,000 → 3,210,000
```

- 취소 창 내내 잔액이 움직이지 않는다. 취소하면 6초 뒤에도 그대로다 (되살아나지 않음)
- 스피너 0개. 서버가 끝냈다고 한 단계만 채워진다
- `NETWORK` 주입 → 실패 화면 → 재시도 → 완료. 잔액이 **정확히 한 번** 빠졌다

## Phase 6 — 여정 7: 발행 · 내역 (완료)

- 발행은 같은 상태 기계·같은 화면을 타고 색과 문구만 바뀐다. 취소 창 8초 (실측 7→5→3→1)
- `screens/History.tsx` · `screens/HistoryDetail.tsx`
- `domain/ledger.ts` — 비율 표기

**발행 문구를 잔액으로 쓰고 있었다.** 발행 중에 헤더가 "아직 보내지 않았다", 본문이
"지금 취소하면 잔액은 그대로다"로 나왔다. 발행이 되돌릴 수 없는 것은 내 잔액이 아니라
총 유통량이다. 화면 전체를 `kind` 로 갈랐다.

**`+0.0%` 는 정보가 아니었다.** 5천만 중 2만을 발행하면 `toFixed(1)` 이 `0.0%` 를 만든다.
크기를 전달하려고 넣은 값이 "변화 없음"으로 읽혔다. `formatRate` 가 값에 따라 유효
자릿수를 바꾸고, 표기 한계보다 작으면 `0.01% 미만` 이라고 쓴다.

**모프와 슬라이드가 싸웠다.** 목록 → 상세를 `layoutId` 공유 요소로 이으면서 화면
슬라이드를 그대로 뒀더니, 이름이 왼쪽(-77px)으로 밀렸다가 되돌아왔다. 같은 정보를
두 모션이 다툰 것이다. `ScreenTransition` 에 `morphGroup` 을 두어 묶음 안 이동에서는
화면을 밀지 않는다. 다시 재니 x 가 고정된 채 y 만 움직인다.

내역 상세에는 **"이체 취소"가 없다.** 되돌릴 수 없는 것을 되돌리는 버튼을 관리자에게도
만들지 않는다 — 그 버튼이 있으면 앱 전체가 "사실 되돌릴 수 있다"는 전제 위에 선다.

## 실기기 검증이 잡아낸 것 (R2)

**금액 입력 화면에서만 검증 신호가 꺼져 있었다.** 같은 `@jisu` 를 화면별로 따라가니
대상 선택 7.88:1 → **금액 입력 헤더 2.56:1** → 확정 7.73:1 이었다. 동명이인을 고른
사용자가 금액을 치는 동안 누구를 골랐는지 확인할 유일한 단서가 가장 흐렸다. 원인은
화면마다 핸들 색을 따로 붙인 것이었다 — 색을 `handle` textStyle 안으로 옮겨 한 곳에서만
정하게 했다. 7.73:1 로 확인.

**핸들과 단위 `P` 가 AA 미달이었다** (밝은 모드 2.56:1). 같은 수정으로 함께 해결됐다.
동명이인 신호는 대비가 아니라 크기·굵기·색상으로 유지된다.

**자동 포커스를 뺐다.** 대상 선택에 들어가면 키보드가 올라와 목록에 남는 세로가
286 CSS px(전체의 37%)뿐이었고, 다섯 명 중 두 명만 보였다. 동명이인 묶음이 아래쪽에
있으면 두 줄을 나란히 볼 수 없다 — 이 화면의 존재 이유가 거기 있는데 자동 포커스가
그걸 가렸다. 사용자도 "목록을 먼저 보고 싶었다"고 답했다.

그대로 둔 것
- 전환 스프링 `520/44/0.8` — "적당하다". 더 올릴 이유가 없다
- 전환 중 글자 소실 — Chrome 10회·Brave 8회 왕복 모두 **0회**. R1-3 은 닫는다
- 프레임 — 120Hz 유지, 간격 중앙값 8.4ms. 뒤로가 109ms 더 길지만 체감에 걸리지 않았다
- 검색이 느린 것은 Mock 설정(지연 700+지터 300 + 디바운스 150)이지 기기가 아니다

## Phase 7 — RN 셸 + 브릿지

여기서부터 안드로이드가 필요하다. 에뮬레이터(`Medium_Phone_API_36.1`)로 대부분 가능하다.

- `react-native-webview` 설치. 개발 중에는 Vite dev 서버를 로드하고 `adb reverse tcp:5173 tcp:5173` 으로 `localhost` 접근
- 브릿지 프로토콜 — 의도만 전달한다
- 시스템 back — `BackHandler` → 브릿지 → 상태 기계가 결정.
  **웹의 `useSystemBack` 히스토리 덫과 겹치지 않게 해야 한다** — 둘 다 살아 있으면
  back 한 번에 `resolveBack` 이 두 번 불린다
- safe area / edge-to-edge (API 35+ 강제)

## Phase 8 — 실기기 검증

에뮬레이터로 확인할 수 없는 것들이다.

- WebView 흔적 제거 확인 — 오버스크롤 바운스, 탭 하이라이트, 텍스트 선택, 롱프레스 메뉴, 더블탭 확대
