# 현장 검증 — 두 세션 운영법

`JOURNEY.md` 의 "확인 방법" 중 절반은 **브라우저에서 확인할 수 없다.** 손가락 크기,
한 손 도달 범위, 스프링의 체감, 실제 GPU 위의 프레임, WebView 티가 나는 순간은
에뮬레이션으로 답이 안 나온다. 그래서 세션을 둘로 나눈다.

## 두 세션

| | 작업 세션 | 실기기 세션 |
|---|---|---|
| 하는 일 | 코드를 쓴다 | 만져보고 기록한다 |
| 저장소 | `web/`, `app/`, `docs/` 전부 | **`docs/FIELD.md` 만** |
| 답할 수 있는 질문 | 상태 기계가 맞나, 계약이 맞나, 토큰이 일관된가 | 눌러지나, 닿나, 부드러운가, 웹처럼 보이나 |
| 답할 수 없는 질문 | 실제로 어떤 느낌인가 | 왜 그렇게 만들었나 |

**핵심 규칙: 실기기 세션은 `web/src` 를 고치지 않는다.** 같은 워크트리를 공유하기
때문이다. 고치고 싶은 것이 생기면 아래 "현장 기록"에 쓰고 작업 세션이 고친다.
관찰과 수정을 한 세션이 겸하면, 관찰이 자기 수정을 정당화하는 방향으로 휜다.

### 공유되는 것은 파일만이 아니다

R2 에서 두 세션이 **같은 브라우저 탭**을 조작하고 있었다는 것이 드러났다. 한쪽이
클릭하지 않았는데 화면이 혼자 바뀌었고, 22:30~22:37 사이의 관측이 서로 오염됐다.
파일만 나눈 규칙으로는 부족하다. 실제로 공유되는 자원이 셋 더 있다.

| 자원 | 증상 | 대처 |
|---|---|---|
| `agent-browser` 의 `default` 세션·탭 | 상대의 클릭이 내 화면에 들어온다 | `AGENT_BROWSER_SESSION` 을 각자 다르게 (`dev` / `field`) |
| Mock 의 인메모리 원장 | 잔액·최근 목록이 서로 오염된다 | 상태에 의존하는 관측은 앞뒤로 원장을 리셋하고 잡는다 |
| 워크트리 파일 | HMR 로 상대의 수정이 내 화면에 즉시 반영된다 | 관측 시작 전에 코드 상태(스프링 값 등)를 기록에 적는다 |

이 호스트는 `--args "--no-sandbox"` 없이는 브라우저가 뜨지 않는다
(`kernel.apparmor_restrict_unprivileged_userns=1`).

## 지금 실기기에서 확인할 수 있는 것 / 없는 것

Phase 7(RN 셸)이 아직 없다. 그래도 폰의 Chrome 으로 개발 서버를 열면 여정 1~6 의
**손의 문제**는 오늘 바로 확인된다.

| 확인 가능 (지금, 폰 Chrome) | Phase 7 이후에만 (WebView 안) |
|---|---|
| 터치 타깃 크기, 한 손 도달 | 오버스크롤 바운스 제거 확인 |
| 화면 전환 스프링의 체감·프레임 | 탭 하이라이트·롱프레스 메뉴 제거 확인 |
| 한글 병기가 실제 글자 크기에서 읽히는가 | safe area / edge-to-edge |
| 다크 모드의 숫자 가독성 | 시스템 back 버튼 |
| 홀드 확정이 스크롤과 충돌하는가 (Phase 4 이후) | 햅틱 · 생체인증 |

## 연결

작업 세션이 개발 서버를 LAN 에 연다.

```bash
cd web && npm run dev:lan          # vite --host
```

**지금 떠 있는 주소: `http://172.30.1.19:5173/`** (호스트 무선 인터페이스 `wlo1`).
폰을 같은 Wi-Fi 에 두고 이 주소를 연다. 주소가 안 열리면 폰과 호스트가 다른 AP 에
붙어 있거나 AP 가 클라이언트 격리를 켠 것이다.

`adb` 로도 붙을 수 있다. 그러면 `adb reverse tcp:5173 tcp:5173` 후
`http://localhost:5173` 이고, 무엇보다 `chrome://inspect` 로 **프레임 실측**이 된다.

**adb 는 무선으로 붙인다.** R1 에서 USB 경로는 끝까지 가지 못했다 (충전 전용 케이블).
무선 순서는 이렇다 — 페어링 포트와 연결 포트가 **다르다**는 점이 함정이다.

```bash
# 폰: 개발자 옵션 → 무선 디버깅 → 기기 페어링 (코드와 ip:port 가 뜬다)
adb pair 172.30.1.31:42905 <6자리 코드>
adb mdns services            # 페어링 후에야 _adb-tls-connect 가 노출된다
adb connect 172.30.1.31:42241
```

페어링만 하고 `adb devices` 를 보면 `offline` 로만 뜬다. 페어링 뒤 mdns 재조회가 필요하다.

**눈으로 본 인상을 프레임 수치로 적지 않는다.** 실측이 안 되면 "부드럽다/걸린다"로만
쓰고, 수치는 adb 가 붙은 뒤에 채운다.

## 채널

기록은 이 파일이 정본이다. 오간 메시지는 사라지지만 파일은 남고, 남아야
`JOURNEY.md` 의 "확인 방법"에 대한 답이 된다. 메시지는 **상대를 깨우는 용도로만** 쓴다.

Orca orchestration Run 하나를 공용 우편함으로 쓴다.

```
run_a09932d74361   포인트 앱 현장 검증 — 작업 세션 ↔ 실기기 세션
```

실기기 세션이 처음 시작할 때 한 번:

```bash
orca orchestration run-use --id run_a09932d74361
```

이후 양쪽 모두:

```bash
orca orchestration send --run run_a09932d74361 --to run:run_a09932d74361 \
  --subject "R1 현장 기록 올림" --body "전환 방향 2건, 눌림 피드백 1건"
orca orchestration check --run run_a09932d74361      # 읽고 읽음 처리
orca orchestration check --run run_a09932d74361 --peek  # 읽음 처리 없이 보기
```

`--from` 에는 **터미널 핸들(`term_...`)만** 넣는다. 사람이 읽는 이름을 넣으면
`stable_pane_required` 로 실패한다. 보통은 생략하면 되고, 그러면 `ORCA_PANE_KEY` 로
자기 터미널이 자동으로 잡힌다.

**중요 — `check` 는 pull 이다.** 상대는 `check` 를 실행하는 순간에만 메시지를 본다.
작업 중인 상대를 실제로 깨우려면 프롬프트에 직접 타이핑한다:

```bash
orca terminal list                                    # 상대 핸들 확인
orca terminal send --terminal <term_...> --enter \
  --text "FIELD.md R1 결정 섹션 업데이트했다. check 해봐."
```

`orca orchestration check --wait --timeout-ms <n>` 로 블로킹 수신도 되지만, 그 세션은
기다리는 동안 아무것도 못 한다. 폰을 만지고 있어야 하는 실기기 세션에는 맞지 않는다.

## 라운드 형식

한 라운드 = 요청 → 기록 → 결정. **결정이 없으면 그 라운드는 끝난 게 아니다.**

기록에는 다음이 들어간다. 없으면 되돌아볼 수 없다.

- 기기 / OS / 브라우저 버전
- 여정의 어느 순간인가
- 무엇을 했나 (재현할 수 있게)
- 무엇이 보였나 (해석 말고 관찰)
- 기대와 다른 점

# R1 — Phase 2 (디자인 시스템 · 화면 전환)

## 확인 요청 · 작업 세션

- [ ] **전환 방향** — 최근 보낸 사람을 탭했을 때 새 화면이 **오른쪽에서** 들어오고,
      뒤로 갔을 때 **왼쪽에서** 들어오는가. 방향을 헷갈리는 순간이 있나
- [ ] **전환 속도** — 스프링(stiffness 420 / damping 42)이 폰에서 굼뜬가 급한가.
      브라우저에서는 적당했는데 이건 데스크톱 GPU 기준이다
- [ ] **전환 중 글자** — 전환 도중 화면 캡처에서 글자가 사라지는 순간이 있었다.
      헤드리스 렌더 아티팩트로 보이지만, 실기기에서 글자가 깜빡이거나 흐려지면
      `will-change: transform` 의 레이어 승격 문제다. **이건 실기기에서만 답이 난다**
- [ ] **눌림 피드백** — 탭 하이라이트를 지웠다. 눌렀는데 눌린 것 같지 않은 요소가 있나
      (최근 목록 행 / 하단 버튼 두 개 / 색 모드 3택)
- [ ] **한 손 도달** — "다른 사람에게 보내기"와 "포인트 발행"에 엄지가 닿나.
      색 모드 3택은 헤더 오른쪽 끝인데, 닿지 않아도 되는 자리라 거기 두었다. 맞나
- [ ] **금액 크기** — `3,240,000 P` 와 `삼백이십사만 포인트`가 팔 길이에서 읽히나.
      한글 병기가 노이즈로 느껴지나
- [ ] **다크 모드** — 자동/밝게/어둡게를 전환할 때 숫자가 뭉개지는 조합이 있나.
      야외 밝기에서도 해보면 좋다

### adb — 무선으로 붙었다

USB 케이블은 PC 에 꽂혀 있었으나 `lsusb` 에 안드로이드 기기가 없었다 (충전 전용 케이블).
폰에서 무선 디버깅을 켠 뒤:

1. `adb mdns services` 비어 있음 (페어링 전)
2. 개발자 옵션 → 무선 디버깅 → 페어링 코드로, `adb pair 172.30.1.31:42905 <코드>` → 성공
3. 페어링 후 `adb mdns services` 에 `_adb-tls-connect._tcp 172.30.1.31:42241` 노출
4. `adb connect 172.30.1.31:42241` → `device`

**즉 FIELD.md 의 "복구 순서"는 이 기기에서 USB 경로로는 끝까지 못 갔고, 무선 페어링이
답이었다.** 페어링 포트(42905)와 연결 포트(42241)가 다르다는 점이 걸린다 — 페어링만
하고 `adb devices` 를 보면 `offline` 로만 뜬다. 페어링 후 mdns 재조회가 필요했다.

프레임 실측 경로가 열렸다.

### R1-1 시스템 back — 페이지를 떠난다

**관찰 시각 ~21:40. 코드 상태: `web/src/ui/useSystemBack.ts` 가 아직 없던 시점.**
(작업 세션이 21:52:52 에 이 파일을 만들었다. 아래 관찰은 그 전의 것이다.)

여정: 홈 → 최근 보낸 사람 탭 → 금액 입력 (`enterAmount`, depth 2)

한 것: 금액 입력 화면에서 안드로이드 back **버튼**.
(정정: 이 기기는 `navigation_mode = 0` — 3버튼 내비게이션이다. 제스처 back 이 아니다.)

보인 것: **앱의 홈으로 돌아가지 않고 페이지를 떠났다.** 돌아오면 앱이 처음부터 다시 로드된다.

화면 안의 뒤로 버튼은 별개로 확인한다 (아래).

기대와 다른 점 — **없다고 볼 수도 있다.** 사용자 지적: "이건 앱이 아니라 웹이니까
당연한 결과다." 맞다. 브라우저에서 back 은 히스토리 back 이고, 앱이 히스토리를 쓰지
않으면 페이지를 떠나는 게 기본 동작이다. 관찰 자체는 놀랍지 않다.

**기록해 두는 이유는 코드의 주석과 어긋나기 때문이다.** `src/App.tsx` 의 `handleBack`
주석은 "웹에서는 브라우저 뒤로가기 (...) 가 이 함수를 부른다" 라고 쓰여 있는데,
`web/src` 어디에도 `popstate` / `history.pushState` 가 없다. 즉 웹에서는 그 경로가
연결되어 있지 않다. 실기기 관찰은 그것과 일치한다.

Phase 7(RN 셸)에서 `BackHandler` 가 붙으면 이 항목은 다시 확인해야 한다. 지금 확인된
것은 "웹에서는 안 붙어 있다" 까지다.

(작업 세션이 21:52:52 에 `520 / 44 / 0.8` 로 바꿨다. 아래는 바뀌기 전의 체감이다.)

스프링 `stiffness 420 / damping 42 / mass 0.9`, `useReducedMotion()` 은 false
(adb 로 확인: `transition/animator/window_animation_scale` 모두 `1.0`, 접근성

프레임 수치는 별도로 잰다 — 눈으로 본 인상과 섞지 않는다.

### R1-3 전환 중 글자 — 깜빡임이 많지는 않다

**관찰 시각 ~21:50. 코드 상태: 스프링 `420 / 42 / 0.9`.**

한 것: 홈 → 최근 보낸 사람 탭 → 화면 안 뒤로 버튼 → 홈. **8회 반복** (5회 요청, 확인차 3회 추가).

보인 것:

- 전환 도중 글자가 깜빡이거나 흐려지거나 사라지는 순간 **0회 / 8회 중**
- 화면 안 뒤로 버튼은 **8회 모두 홈으로 정상 복귀** (시스템 back 과 달리 앱 안에서 처리된다)

**헤드리스 캡처에서 보였던 글자 소실은 실기기에서 재현되지 않았다.** 이 항목은
"실기기에서만 답이 난다"고 적혀 있던 것이고, 답은 "실기기에서는 안 보인다" 이다.
`willChange: 'transform'` 의 레이어 승격 문제로 볼 근거가 이 기기·이 브라우저에서는 없다.

주의: Brave Nightly 1.95.76 에서의 결과다. Chrome 에서는 확인하지 않았다.

### R1-4 계측 방법 — `gfxinfo` 는 웹 프레임을 세지 않는다

`adb shell dumpsys gfxinfo <브라우저 패키지>` 로는 화면 전환 프레임을 잴 수 없다.
전환 8회를 돈 뒤에도 `Total frames rendered: 28` 이었다. 이 값은 브라우저의 **안드로이드
뷰**(툴바 등) HWUI 프레임이고, 웹 페이지 애니메이션은 Chromium 자체 컴포지터가 별도
서피스에 그리기 때문에 여기 안 잡힌다.

되는 방법:

```bash
adb shell dumpsys SurfaceFlinger --list | grep -i brave     # 레이어 이름 확인
adb shell dumpsys SurfaceFlinger --latency \
  "com.brave.browser_nightly/ChromeChildSurface#340338"
```

`ChromeChildSurface` 가 웹 컨텐츠 서피스다 (`ChromeNativeWindowSurface` 는 0 만 나온다).
출력은 128행 링버퍼이고 열은 `desiredPresent / actualPresent / frameReady` (ns).
`actualPresent` 의 차분이 프레임 간격이다. 유휴 상태에서는 프레임이 생기지 않으므로,
**전환 직전에 2초 정지 → 전환 1회 → 정지** 후 덤프하면 그 전환만 깨끗하게 담긴다.

첫 행의 `41666665` (= 24Hz) 는 유휴 상태 값이라 **믿으면 안 된다.** 실측 간격이 정답이고,
이 기기에서는 전환 중 간격 중앙값이 **8.4ms (약 119Hz)** 로 나왔다. 디스플레이가
120 / 96 / 60 fps 모드를 지원하고, 전환은 120Hz 로 그려지고 있다.

### R1-5 측정 중에 코드가 바뀌었다 — 이 라운드의 프레임 수치는 버렸다

21:53 에 "앞으로 1회" 전환을 깨끗하게 재려던 참에, 33초 전인 **21:52:52 에 작업 세션이
`ScreenTransition.tsx` 의 스프링을 `420/42/0.9` → `520/44/0.8` 로 바꿨다.** 같은 시각에
`useSystemBack.ts` 도 새로 생겼다. 우편함에는 알림이 없었다.

덤프에는 578ms / 570ms 짜리 버스트 두 개가 잡혔는데, 하나는 사용자의 전환이고 하나는
HMR 리로드 리페인트로 보인다. **어느 쪽이 어느 스프링인지 구분할 수 없어 수치를 버렸다.**

이건 이 파일 앞부분의 두 세션 규칙에 빠져 있는 항목이다. 규칙은 "실기기 세션이 `web/src`
를 고치지 않는다" 까지만 말하는데, 반대 방향도 필요하다:

> **작업 세션이 `web/src` 를 고치면 실기기 세션의 진행 중인 측정이 무효가 된다.**
> HMR 이 폰에 즉시 반영되기 때문이다. 고친 뒤에는 우편함에 알려야 하고, 실기기 세션은
> 측정 전에 하드 리로드로 코드 상태를 확정해야 한다.

현장 기록의 모든 항목에 **관찰 시각과 그때의 코드 상태**를 같이 적기로 한다. 없으면
나중에 그 관찰이 무엇에 대한 것이었는지 알 수 없다. 위의 R1-1 ~ R1-3 에 소급 적용했다.

## 결정 · 작업 세션

### R1-1 시스템 back — 고쳤다. 관찰은 맞았고 지적이 더 맞았다

"웹이니까 당연하다"가 맞다. 그런데 기록해 둔 이유 — **코드 주석이 거짓말이었다** — 가
더 중요했다. `App.tsx` 는 "웹에서는 브라우저 뒤로가기가 이 함수를 부른다"고 써 있었지만
`popstate` 를 듣는 곳이 없었다. `resolveBack` 은 이 앱의 핵심 판단인데, 그것을 실제로
부르는 경로가 웹에 하나도 없었다는 뜻이다. 테스트에서만 맞는 코드였다.

`ui/useSystemBack.ts` 를 만들어 히스토리에 **덫을 하나** 놓는다. back 을 누르면 덫이
튀고, 상태 기계가 소비했으면 덫을 다시 놓아 그 자리에 머문다. 소비하지 않았으면
(`exit`) 한 칸 더 물러나 진짜로 나간다. 히스토리에 화면이 쌓이지 않으므로 라우터가
아니고, back 의 의미는 여전히 `resolveBack` 혼자 정한다.

브라우저 검증 (360×780): 금액 화면에서 back → 홈 (페이지 유지, JS 전역 살아 있음).
홈에서 back → `about:blank` (앱을 떠난다).

이걸 고쳐서 얻는 것: 여정 5 의 "보내는 중에는 back 이 아무것도 하지 않는다"를
Phase 7 을 기다리지 않고 폰에서 확인할 수 있게 됐다.

### R1-2 전환 속도 — 올렸다. 다시 판단해 달라

`stiffness 420 / damping 42 / mass 0.9` → **`520 / 44 / 0.8`**. 대략 20% 빨라진다.
한 사람의 한 번 관찰이지만 추측으로 만든 값을 실측 인상보다 우선할 이유가 없다.
R2 에서 다시 본다 — 이번에도 느리면 더 올리고, 급해졌으면 되돌린다.

### R1-3 전환 중 글자 — 유지. 대신 조건을 좁혀 다시 묻는다

"많지 않다"로는 판단할 수 없다. `will-change: transform` 은 그대로 둔다 (빼면 보통
악화된다). R2 에서 **Chrome 으로** 횟수를 세어 달라 — Brave Nightly 의 렌더 버그와
구분되지 않는다는 지적이 맞다.

### 요청서의 잘못 — 브라우저를 특정하지 않았다

R1 요청서가 "폰 Chrome" 을 전제로 쓰였는데 지시에는 그 말이 없었다. 앞으로는 요청마다
어느 브라우저인지 적는다. 렌더 관련 항목은 **Chrome 고정**이다.

### 덤으로 잡은 것 — 360×780 에서 금액이 잘렸다

실기기 CSS 뷰포트가 360×780 이라는 기록을 보고 그 폭에서 다시 재 봤다. 13자리를 넣으면
금액과 한글이 오른쪽에서 잘렸다. **보낼 금액을 읽을 수 없게 되는 것**이라, 자릿수 오타를
막으려고 만든 화면이 자릿수를 감추고 있었다.

`ui/amountFit.ts` — 자릿수에 따라 글자 크기를 세 단계로 줄인다. 실제 폭을 재지 않고
자릿수로 정하는데, 측정은 렌더 후에야 가능해서 한 프레임 동안 잘린 상태가 보이고
그 한 프레임이 하필 사용자가 금액을 확인하는 순간이기 때문이다. 한글 표기는 줄바꿈을
허용했다 (`keep-all`) — 두 줄이 되어도 읽는 데 지장이 없고, 잘리는 것보다 낫다.

### R2-4 전환 프레임 실측 — 120Hz 를 유지한다

계측: `dumpsys SurfaceFlinger --latency "com.android.chrome/ChromeChildSurface#340520"`.
각 전환 전후로 정지해서 버스트를 분리했다 (앞뒤 공백 79초 / 243초 — 다른 활동과 섞이지 않았다).

| | 프레임 | 지속 | 간격 중앙값 | 최대 간격 | 16.7ms 초과 |
|---|---|---|---|---|---|
| 앞으로 (홈 → 금액) | 50 | **436ms** | 8.4ms (119Hz) | 25.1ms | 2 |
| 뒤로 (금액 → 홈, 화면 안 뒤로 버튼) | 58 | **545ms** | 8.4ms (119Hz) | 50.3ms | 4 |

읽는 법:

- 간격 중앙값이 양방향 모두 **8.4ms** 다. 전환 내내 120Hz 로 그려지고 있고,
  60Hz 로 떨어지지 않는다. 사용자가 "적당하다"고 한 것과 어긋나지 않는다
- **뒤로가 앞으로보다 109ms 길고, 끊긴 프레임도 2배다.** 최대 간격 50.3ms 는
  120Hz 기준 6프레임에 해당한다. 뒤로 갈 때는 홈이 다시 마운트되면서 데이터를 다시
  읽는 구간이 겹친다 — 다만 **원인을 실측으로 가른 것은 아니다.** 관찰은
  "뒤로가 더 길고 더 끊긴다"까지다
- 사용자는 이 끊김을 **말로 보고하지 않았다** (체감은 "적당하다"). 50.3ms 한 번은
  눈에 걸리지 않는 크기라는 뜻으로 읽힌다

  때문이다.** `groupHomonyms` 는 같은 이름을 붙여 놓지만, 그 묶음이 목록의 4번·5번에
  있으면 **키보드에 가려 두 줄이 함께 눈에 들어오지 않는다.** "비교는 두 줄이 눈에 함께
  들어올 때만 일어난다"는 주석의 전제가, 키보드가 올라온 실기기에서는 위치에 따라 깨진다
- 이건 브라우저에서는 안 보인다. 데스크톱 뷰포트에는 5명이 다 들어간다
- Chrome 자동완성 바(열쇠·카드·핀 아이콘)가 목록과 키보드 사이에 한 줄 더 들어간다.
  이건 브라우저 UI 라 Phase 7 의 WebView 에서는 사라진다. 다만 **키보드 자체는 남는다**

판단은 작업 세션 몫이다. 관찰은 "키보드가 올라온 상태에서 목록은 두 줄"까지다.

### R2-6 자동 포커스는 방해였다 · 헤더는 누구인지 말해준다 · 검색 지연은 mock 이 만든 것

**Chrome 151, 3버튼 내비게이션(`navigation_mode = 0`).**

**자동 포커스 — 방해다.** 대상 선택 화면에 들어가자마자 키보드가 올라온다.
사용자의 말: **"목록을 먼저 보고 싶었다."** R2-5 의 실측과 겹친다 — 키보드가 올라온
상태에서 목록은 두 줄뿐이라, 먼저 보고 싶은 목록이 실제로 가려져 있다.

즉 이 항목은 취향 문제가 아니다. 자동 포커스가 **화면의 63% 를 덮은 채로 시작한다.**

**잘못 고르기 — 화면이 말해준다 (합격).** 김지수 두 명 중 두 번째(`@jisu`)를 골랐고,
금액 화면 헤더가 **`김지수 @jisu`** 로 이름과 핸들을 나란히 보여준다. 사용자는 기억이
아니라 화면을 보고 `@jisu` 임을 알아봤다. 여정 2 의 시험은 통과한다.

다만 캡처에서 걸리는 것: **대상 선택 화면에서 주황색이던 핸들이 금액 화면 헤더에서는
회색(`fg.subtle`)이다.** 동명이인을 골랐을 때야말로 핸들이 검증 대상인데, 검증이 필요한
마지막 화면에서 색이 죽는다. 사용자가 알아봤으므로 실패는 아니다 — 눈에 걸린 것으로만 적는다.

**핸들 검색이 살짝 느리다 — 원인은 mock 이다.** 사용자가 "핸들 검색이 살짝 느린 느낌"
이라고 했다. 폰이나 렌더 문제가 아니다:

- `api/sim.ts` — `latencyMs: 700, jitterMs: 300` (의도적으로 넣은 서버 지연)
- `api/useUserSearch.ts` — `DEBOUNCE_MS = 150`

즉 글자를 멈춘 뒤 **850~1150ms** 뒤에 결과가 바뀐다. 실기기가 느린 게 아니라 설계값이다.
이 값이 실기기에서 어떻게 느껴지는지가 관찰의 내용이고, 답은 **"살짝 느리다"** 이다.

**한글 IME** — 이 라운드에서 확인하지 못했다. 사용자가 핸들(영문) 검색 인상만 보고했다.
조합 중 깨짐 / 커서 튐 / 마지막 글자 사라짐은 다음 라운드로 넘긴다.

### R2-7 키패드 기하 — 캡처에서 실측했다. 크기 요구는 충족한다

**Chrome 151, 금액 입력 화면 스크린샷(1080x2340, DPR 3)에서 픽셀로 잰 값.**
이 기기는 density 480 이므로 **1 CSS px = 1 dp** 다.

키 글자 중심 좌표 (device px):

| | x=217 | x=540 | x=864 |
|---|---|---|---|
| y=1311 | 1 | 2 | 3 |
| y=1492 | 4 | 5 | 6 |
| y=1671 | 7 | 8 | 9 |
| y=1851 | 만 | 0 | ⌫ |

- **행 간격 180 device px = 60 CSS px** (세 간격이 181/179/180 으로 균일)

- 즉 키 하나가 **108 x 60 CSS px (= 108 x 60 dp)**

`보내기 확인` 버튼: 중심 (539, 2066) device px, **320 x 54 CSS px**, 좌우 여백 20px.

다만 캡처에서 걸리는 것 — **키에 테두리도 배경도 없다.** 숫자 글자만 떠 있고 키의
경계가 시각적으로 없다. 크기가 60dp 여도 **사용자는 그 60dp 가 어디부터 어디까지인지
모른 채 누른다.** 오타가 나는지, 경계가 없는 게 불안한지는 손으로만 답이 난다.
사용자가 돌아오면 확인할 항목으로 남긴다.

### R2-8 자율 QA 는 진행할 수 없다 — 기기가 사라졌다

**22:24 시점. 사용자가 폰을 들고 외출했다.**

- `adb devices` → `offline`, 이어서 목록에서 사라짐

- `adb mdns services` → 비어 있음
- `ping 172.30.1.31` → **응답은 온다. 다만 RTT 295~382ms** (LAN 치고 비정상적으로 높다)
- 개발 서버(`172.30.1.19:5173`)는 200 으로 살아 있다

폰이 같은 네트워크에는 남아 있지만 절전으로 잠들었고, 무선 디버깅 리스너가 닫혔다.
**adb 로 화면을 보거나 조작할 수 없다.** 사람 없이 진행하는 QA 도 adb 를 전제로 하므로
같이 막힌다 — `input tap` 도 `screencap` 도 기기가 있어야 한다.

복구 순서 (사용자가 돌아오면):

1. 폰 화면을 켜고 같은 Wi-Fi 확인
2. 개발자 옵션 → 무선 디버깅이 **꺼져 있으면 다시 켠다**
3. 호스트에서 `adb mdns services` — `_adb-tls-connect._tcp` 로 **새 포트**가 뜬다
   (포트는 매번 바뀐다. 42241 은 이제 유효하지 않다)
4. `adb connect 172.30.1.31:<새 포트>`
5. 페어링은 유지되므로 `adb pair` 는 다시 하지 않아도 된다

**돌아오면 바로 자동화할 수 있게 준비해 둔 것** — 위 R2-7 의 좌표로 사람 손 없이
다음이 가능하다. 화면 크기가 같고 레이아웃이 안 바뀌었다는 전제다:

```bash
T() { adb shell input tap "$1" "$2"; }
# 13자리 잘림 확인: 1 을 13번
for i in $(seq 13); do T 217 1311; done
adb exec-out screencap -p > long13.png
# 30만: 3 → 0 → 만  /  잔액 초과: 9 를 여러 번
# 색 모드 3택은 홈 헤더 오른쪽 끝
```

**주의 — 좌표는 금액 입력 화면 한정이고, 작업 세션이 Phase 4/5/6 을 구현 중이라
레이아웃이 바뀌면 무효다.** 자동화 전에 반드시 `screencap` 으로 화면을 먼저 확인한다.

## B-3 동명이인 강조는 작동한다 — 그런데 마지막 화면에서 풀린다

`useUserSearch.ts` 주석은 "화면은 겹칠 때만 핸들을 키워야 한다 — 항상 크게 두면 검증
신호가 아니라 배경이 된다" 라고 말한다. **그 판단은 실제로 작동한다.** 대상 선택 화면
(밝게) 실측:

| | 색 | 크기/굵기 | 대비 |
|---|---|---|---|
| **동명이인** 핸들 `@jisoo` `@jisu` | `rgb(146,49,10)` | **16px / 500** | **7.88** |
| "같은 이름 2명 · 핸들로 구분한다" | `rgb(146,49,10)` | 12px / 500 | 7.88 |
| 동명이인 아닌 핸들 `@taeyun` 등 | `rgb(161,161,170)` | 14px / 400 | 2.56 |

겹칠 때만 색·크기·굵기가 셋 다 올라간다. 2.56 → 7.88 은 **3배 차이**다. 의도대로다.

**문제는 그 사람을 고른 다음이다.** 같은 `@jisu` 가 화면마다 이렇게 달라진다:

| 화면 | 색 | 크기 | 대비 (밝게) |
|---|---|---|---|
| 대상 선택 (고르는 순간) | 주황 | 16px / 500 | **7.88** |
| **금액 입력 헤더** | 회색 | 14px / 400 | **2.56** |
| 확정 화면 (`이렇게 보낸다`) | 진회색 | 14px / 400 | 7.73 |

즉 **금액 입력 화면에서만 검증 신호가 꺼진다.** 동명이인을 고른 사용자가 금액을 치는
동안, 자기가 두 김지수 중 누구를 골랐는지 확인할 유일한 단서가 2.56 으로 내려앉는다.
확정 화면에서 7.73 으로 되살아나지만, 그때는 이미 금액을 다 친 뒤다.

이건 실기기에서 사용자가 말한 것과 같은 것을 가리킨다 — R2-6 에 "대상 선택에서 주황이던
핸들이 금액 화면 헤더에서는 회색이다" 라고 눈으로 적어 두었고, 여기서 수치가 붙었다.
다만 **사용자는 그래도 `@jisu` 를 알아봤다.** 실패가 아니라 약한 자리다.

- **짧은 클릭 → 발동하지 않는다.** 확정 화면에 그대로 머문다. 여정 4 가 막으려던
  "읽지 않고 누르기"와 "스크롤하다 스치는 오터치"에 대해 이 속성이 성립한다
- **홀드(600ms 이상) → 발동한다.** `Sending` 을 거쳐 `Done` 으로 간다
- 홀드 경로가 포인터와 키보드 둘 다 있다 (`onPointerDown` / 스페이스·엔터 keydown).
  키보드로도 확정할 수 있다

`Done` 화면: `✓ 보냈다 / 김지수 @jisoo / 30,000 P / 남은 잔액 3,210,000 P / 확인`.
잔액이 3,240,000 → 3,210,000 으로 실제로 줄었다.

`Failed` 화면(주입된 `NETWORK` 실패): `보내지 못했다 / 요청이 서버에 닿지 못했다 /
지금 확실한 것 — 서버가 요청을 받았는지 알 수 없다`. 여정 6 의 "돈의 위치를 모름"에
대해 모른다는 것을 모른다고 쓰고 있다.

**600ms 가 오터치를 막기에 충분한지, 스크롤과 충돌하는지, 손이 언제 떨어지는지는
브라우저로 답이 나지 않는다.** 폰에서 확인할 항목으로 남긴다.

## B-7 우리 둘이 같은 브라우저 탭을 조작하고 있었다

**파일을 나누는 것만으로는 두 세션이 분리되지 않는다.** 최소한 다음이 필요하다:

- 브라우저는 세션 이름을 나눈다 (`AGENT_BROWSER_SESSION`)
- `web/src` 를 고치면 우편함에 한 줄 남긴다 (측정 중인 쪽이 판단할 수 있게)

## B-9 여정 5 전 구간 타임라인 — 스피너 0, 단계 역행 없음

CLI 왕복이 3초 취소 창보다 느려서, 페이지 안에 **100ms 기록기**를 심어 타임라인을
통째로 받았다 (`setInterval` 로 `innerText` 와 무한 반복 CSS 애니메이션 개수를 샘플링).
개발자 패널에서 단계 속도를 `각 2초` 로 늦춘 상태다.

```
  101ms  이렇게 보낸다 · 박태윤 @taeyun · 20,000P · 보낸 뒤 남는 잔액 3,140,000 P
 8401ms  아직 보내지 않았다 · 3초 후 보냅니다
         "아직 아무것도 처리되지 않았다. 지금 취소하면 잔액은 그대로다." · [취소]
 9001ms  2초 후 보냅니다
10001ms  1초 후 보냅니다
11001ms  보내는 중 — 내 잔액에서 출금 / 이체 요청 전송 / 원장 검증 / 받는 사람에게 입금
13001ms  ✓ 출금
15001ms  ✓ 출금  ✓ 전송
17001ms  ✓ 출금  ✓ 전송  ✓ 검증
19401ms  ✓ 보냈다
```

- **스피너 0개.** 전 구간에서 `animation-iteration-count: infinite` 인 요소가 **하나도 없다.**
  요청서의 "0이어야 한다"를 충족한다
- **단계 역행 없음.** ✓ 개수가 0 → 1 → 2 → 3 으로 단조 증가한다. 건너뛴 단계도, 되돌아간
  단계도 없다. 세 번의 이체에서 모두 같았다
- **취소 창 카운트다운이 실제로 1초 간격이다** (2601 → 3601 → 4601ms)
- 진행 화면에 "처리가 시작되어 취소할 수 없다"가 함께 있다. 취소 창과 진행 화면이
  취소 가능 여부를 **서로 반대로, 명시적으로** 말한다

## B-10 완료 화면이 약 0.5초 동안 **이체 전 잔액**을 보여준다

**네 번의 이체에서 네 번 다 재현됐다.**

|---|---|---|---|
| 20,000 (3,160,000 기준) | **3,160,000 P** | 3,140,000 P | 500ms |
| 10,000 (3,140,000 기준) | **3,140,000 P** | 3,130,000 P | 398ms |
| 70,000 (3,130,000 기준) | **3,130,000 P** | 3,060,000 P | 500ms |
| 60,000 (3,020,000 기준) | **3,020,000 P** | 2,960,000 P | 498ms |

즉 `✓ 보냈다` 와 함께 뜨는 **"남은 잔액"이 처음 약 0.4~0.5초 동안 아직 안 빠진

이건 여정 5 가 막으려던 **"거짓 완료"** 에 해당한다고 본다. 화면이 "보냈다"고 단정하면서
동시에 보내기 전의 잔액을 "남은 잔액"이라는 이름으로 보여주는 구간이 있다. 0.5초는
짧지만, 완료 화면에서 사용자가 가장 먼저 보는 숫자가 그것이다.

**다만 이건 mock 의 지연(700~1000ms) 위에서 잰 값이다.** 실제 서버 지연이 다르면 길이도
달라진다. 판단은 작업 세션 몫이다.

## B-11 취소 창 정직성 — 잔액이 1P 도 움직이지 않는다

CLI 로는 3초 창을 못 잡아서, 페이지 안에 **자동 취소 감시자**를 심었다 (50ms 마다
`취소` 버튼을 찾아 발견 즉시 `click()`).

- 취소 직전 잔액 **3,020,000 P**
- 취소 창 진입 2101ms → 자동 취소 → **2904ms 에 홈**
- 홈의 잔액 **3,020,000 P — 불변**
- 그 뒤 **15초간 5초 간격으로 3회 확인, 계속 3,020,000 P.** 되살아나지 않는다

취소 창 문구("아직 아무것도 처리되지 않았다. 지금 취소하면 잔액은 그대로다")가
실제 동작과 일치한다.

## B-12 멱등성 — 실패 후 재시도해도 한 번만 빠진다

개발자 패널에서 `네트워크` 실패를 주입했다.

1. 이체 전 잔액 **3,020,000 P**, 60,000 P 를 최준호에게
2. 홀드 → **1901ms 에 곧장 실패 화면.** 취소 창도 진행 4단계도 거치지 않는다
3. 실패 시점 잔액 **3,020,000 P — 차감 없음**
4. `다시 시도` → **확정 화면으로 되돌아간다** (바로 재전송하지 않는다. 다시 홀드해야 한다)
5. 다시 홀드 → 취소 창 → 4단계 → 완료
6. 최종 잔액 **2,960,000 P**

**3,020,000 − 60,000 = 2,960,000. 정확히 한 번만 빠졌다.** 실패한 시도는 차감하지 않았고,
재시도가 이중 처리되지 않았다. 화면이 약속한 "다시 시도해도 두 번 처리되지 않는다"가
지켜진다.

걸리는 것 하나: **실패가 주입되면 취소 창과 진행 4단계를 건너뛴다** (확정 1502ms →
실패 1901ms). 요청이 나가기 전에 끊긴 경우로 보이지만, 사용자 입장에서는 홀드하자마자
실패가 뜨는 셈이라 "보내는 중"을 본 적이 없다. 의도한 것인지는 작업 세션이 판단할 일이다.

## B-13 실패 문구 두 종류가 돈의 위치를 다르게 말한다

| | 네트워크 | 잔액 부족 |
|---|---|---|
| 제목 | 보내지 못했다 | 보내지 못했다 |
| 이유 | 요청이 서버에 닿지 못했다 | 잔액이 부족하다 |
| 라벨 | **지금 확실한 것** | **돈은 여기 있다** |
| 본문 | 서버가 요청을 받았는지 **알 수 없다**. 다시 시도해도 두 번 처리되지 않는다 — 같은 요청으로 취급된다 | **아무것도 나가지 않았다. 잔액은 그대로다** |
| 버튼 | **다시 시도** / 금액 고치기 / 홈으로 | 금액 고치기 / 홈으로 |

**두 화면이 다르게 말한다 — 요청서가 물은 것이 그대로 성립한다.** 애매한 실패에는
"알 수 없다"고 쓰고, 단정할 수 있는 실패에는 "돈은 여기 있다"고 쓴다.

그리고 **`다시 시도` 버튼이 잔액 부족 화면에는 아예 없다.** 결정적 실패라 다시 눌러도
같은 결과이기 때문이다. 버튼의 유무로 재시도가 의미 있는지를 말한다.

## B-14 발행 경로 — 전 구간이 이체와 분리된다. 겹치는 곳은 한 군데뿐

**세션 `field`, 어둡게. 발행 경로 전체를 끝까지 따라갔다.**

문구가 갈린다. **"잔액"이라는 말이 발행 경로에 한 번도 나오지 않는다.**

| | 이체 | 발행 |
|---|---|---|
| 대상 선택 | 누구에게 보낼까 | 누구에게 **발행**할까 |
| 금액 화면 상한 | 보낼 수 있는 금액 | **남은 발행 여력** |
| 확정 제목 | 이렇게 보낸다 | 이렇게 **발행**한다 |
| 확정 본문 | 지금 잔액 / 보낸 뒤 남는 잔액 | 지금 **총 유통량** / 발행 뒤 **총 유통량** / **유통량 변화 +0.1%** |
| 확정 버튼 | 꾹 눌러서 보내기 | 꾹 눌러서 **발행** |
| 취소 창 | 아직 보내지 않았다 · **3초** | 아직 발행하지 않았다 · **8초** |
| 취소 창 본문 | 지금 취소하면 **잔액**은 그대로다 | 지금 취소하면 **총 유통량**은 그대로다 |
| 진행 4단계 | 내 잔액에서 출금 / 이체 요청 전송 / 원장 검증 / 받는 사람에게 입금 | **발행 준비 / 원장에 기록 / 유통량 검증 / 받는 사람에게 지급** |
| 완료 | ✓ 보냈다 · 남은 잔액 | ✓ **발행했다** · **총 유통량** |

색도 갈린다. 이체는 파랑 `rgb(37,99,235)`, 발행은 보라 `rgb(192,132,252)`.
완료 화면의 ✓ 배지도 이체는 초록, 발행은 보라(`rgb(26,3,46)` on 보라, 7.25)다.

8초 카운트다운이 실제로 1초 간격이다 (2501 → 3501 → … → 8501ms).

**겹치는 곳이 딱 하나 있다.** 발행 **완료** 화면의 `확인` 버튼 배경이 `rgb(37,99,235)` —
**이체의 파랑**이다. 그 화면의 다른 모든 요소는 보라 계열이다. 중립적인 닫기 동작이라
의도한 것일 수도 있으나, "발행 경로 전체에서 색이 겹치는 화면이 있는지" 물었으므로 적는다.

## B-15 B-10 은 이체만의 문제가 아니다 — 발행 완료에서도 재현된다

```
18001ms  ✓ 발행했다 · 총 유통량  50,000,000 P   ← 발행 전 값
18401ms  ✓ 발행했다 · 총 유통량  50,050,000 P   ← 400ms 뒤 갱신
```

이체 완료 화면의 "남은 잔액"과 같은 자리에서 같은 일이 일어난다. 완료 화면이
**"했다"고 단정하면서 아직 반영 안 된 숫자를 함께 보여주는 구간**이 양쪽 경로에 다 있다.
한 화면의 문제가 아니라 완료 화면의 데이터 조회 방식 문제로 보인다.

## B-16 내역 모프 — 슬라이드와 싸우지 않는다

50ms 간격으로 **(1) `position:absolute` 이면서 transform 이 걸린 레이어의 가로 이동량**과
**(2) 이름 텍스트의 화면 좌표**를 함께 기록했다.

**내역 목록 → 상세** (`history` 1 → `historyDetail` 2, 깊이가 커지므로 원래대로면 슬라이드):

```
 51ms  가로 레이어 없음   이름 y=136
101ms  가로 레이어 없음   이름 y=130
201ms  가로 레이어 없음   이름 y= 90
351ms  가로 레이어 없음   이름 y= 71
451ms  가로 레이어 없음   이름 y= 68   ← 안정
```

- **가로로 미는 레이어가 하나도 없다.** 화면이 옆으로 밀리지 않는다
- 이름의 **x 는 20 으로 고정**, **y 만 136 → 68 로 올라간다.** 폰트 크기도 18px 유지
- 즉 눌린 줄이 상세 화면의 제목 자리로 **자리를 옮긴다**. 모프가 성립한다

**계측기가 슬라이드를 실제로 잡는지 검증했다** — 홈 → 금액 입력(깊이 0 → 2)에서:

```
 54ms  x=[-21, 291]   이름 x= 53
153ms  x=[-88,  66]   이름 x=-14
403ms  x=[-108,  1]   이름 x=-34
451ms  x=[-108]                     ← 안정
```

나가는 레이어가 `-21 → -108`(왼쪽으로), 들어오는 레이어가 `291 → 0`(오른쪽에서).
`ScreenTransition` 의 `enter x:100% / exit x:-30%` 와 일치한다. 슬라이드 구간은
**약 450ms** 로, 폰에서 잰 436ms(R2-4)와 맞는다.

**계측기는 슬라이드를 잡는다. 그런데 내역 전환에서는 아무것도 안 잡혔다.** 결론:
내역 목록↔상세는 슬라이드가 아니라 모프이고, 둘이 겹쳐 일어나지 않는다.

## B-17 확정 화면의 자릿수 — 13자리는 확정에 도달할 수 없다

- 금액 입력에서 `1` 을 13번 눌러 `1,111,111,111,111` 을 만들면 **`보내기 확인` 이 disabled** 다.
  잔액 초과 경고가 뜨고 다음으로 못 간다. **즉 확정 화면이 13자리를 볼 일이 없다**
- 확정 화면이 실제로 감당해야 하는 최대는 발행 경로다. 발행 여력 전액(49,950,000)을
  걸면 확정 화면이 `발행 뒤 총 유통량 **100,000,000 P**`(9자리)와 `유통량 변화 +99.8%`를 함께 띄운다
- 그 상태에서 **넘치는 요소가 하나도 없다.** `document.scrollWidth == innerWidth == 360`,
  `scrollWidth > clientWidth` 인 요소 0개, 뷰포트 밖으로 나간 요소 0개

## B-18 새 화면 대비 재측정 — 진행 화면의 **미도달 단계**가 AA 미달이다

어둡게(배경 `rgb(9,9,11)`) 기준. 취소 창 · 실패 · 완료 · 내역은 전부 통과한다.

| 화면 | 최저 대비 요소 | 값 |
|---|---|---|
| 취소 창 | 본문 "아직 아무것도 처리되지 않았다…" | 7.76 |
| 완료 (이체/발행) | `확인` 버튼 (흰 글자/파랑) | 5.17 |
| 실패 | `다시 시도` (흰 글자/파랑) | 5.17 |
| 실패 | 라벨 "지금 확실한 것" (12px/500) | 5.81 |
| 발행 금액 | `발행 확인` (`rgb(26,3,46)` on 보라) | 7.25 |

**진행 화면만 다르다:**

| 요소 | 색 | 크기/굵기 | 대비 |
|---|---|---|---|
| `내 잔액에서 출금` (현재 단계) | `rgb(250,250,250)` | 16px / 500 | 19.06 |
| **`이체 요청 전송`** (미도달) | `rgb(113,113,122)` | 16px / 400 | **4.12** ✗ |
| **`원장 검증`** (미도달) | `rgb(113,113,122)` | 16px / 400 | **4.12** ✗ |
| **`받는 사람에게 입금`** (미도달) | `rgb(113,113,122)` | 16px / 400 | **4.12** ✗ |
| `처리가 시작되어 취소할 수 없다` | `rgb(161,161,170)` | 14px / 400 | 7.76 |

**B-2 에서 핸들에 있던 바로 그 색 토큰(`rgb(113,113,122)`)이 여기 남아 있다.**
핸들 쪽은 `handle` textStyle 로 모으면서 걷어냈지만, 진행 화면의 미도달 단계는 그대로다.
16px/400 이라 large text 예외에도 걸리지 않는다.

**밝은 모드에서는 더 나쁘다.** 같은 화면을 `밝게` 로 바꿔 다시 쟀다
(배경 `rgb(255,255,255)`):

| 요소 | 색 | 대비 (밝게) | 대비 (어둡게) |
|---|---|---|---|
| `내 잔액에서 출금` (현재 단계) | `rgb(9,9,11)` | 19.9 | 19.06 |
| **미도달 3단계** | `rgb(161,161,170)` | **2.56** ✗ | 4.12 ✗ |
| `처리가 시작되어 취소할 수 없다` | `rgb(82,82,91)` | 7.73 | 7.76 |

**B-2 와 정확히 같은 패턴이다** — 밝은 모드가 어두운 모드보다 나쁘고, 문제가 되는 값도
그때와 같은 `rgb(161,161,170)` / **2.56** 이다. 핸들에서 걷어낸 문제가 진행 화면에
그대로 남아 있고, 두 모드 모두 AA 아래다.

**흐리게 만든 것이 의도라는 건 안다** — 어디까지 왔는지를 밝기로 말하는 설계다. 다만
미도달 단계도 "앞으로 무슨 일이 일어나는지"를 읽히게 해야 하는 정보다. 밝기 차이를
유지하면서 둘 다 4.5 위에 두는 선택지가 있는지는 작업 세션이 판단할 일이다.

## B-19 내역 화면 — 취소된 건을 취소선으로 구분한다

목록 한 줄은 `이름 / (발행 ·) 상태 · 시각 / 금액` 이다.

- **발행은 초록 `+50,000P`, 이체는 흰색 `−60,000P`.** 부호와 색 둘 다로 방향을 말한다
- **취소된 건은 이름과 금액에 취소선이 그어지고 회색으로 내려간다.** 라벨은 `취소됨`,
  시각은 없다. 처음 텍스트만 봤을 때는 `−80,000P` 가 돈이 나간 것처럼 읽힐까 걱정했는데,
  화면에서는 취소선이 그것을 막는다
- 상세 화면에는 보낸 사람 / 받은 사람 / 요청 시각 / 확정 시각 / `진행 4 / 4 단계` /
  **`요청 키 f400a938-01a9-…`** 가 있다. 실패 화면이 약속한 "같은 요청으로 취급된다"의
  근거를 화면에서 확인할 수 있게 해 둔 것으로 읽힌다

## B-20 우편함 알림의 절반은 내가 보낸 것이다

`--to run:run_a09932d74361` 은 **보낸 사람도 수신자에 포함한다.** 두 세션 모두 그 Run 에
속하므로, 내가 보낸 메시지가 나에게도 배달되고 "메시지 N건" 알림이 뜬다.

실제로 R3 구간에서 알림 세 번이 연속으로 **전부 내가 보낸 메시지의 되돌아옴**이었다.
`inbox --full` 로 열어야 그걸 알 수 있으므로, 알림 숫자만 보고 상대가 응답했다고
판단하면 안 된다.

에코를 피하려면 상대 터미널 핸들로 직접 보내면 된다:

```bash
orca orchestration send --run run_a09932d74361 --to term_<상대 핸들> ...
```

다만 그러면 Run 우편함에 남지 않는다. 이 파일이 정본이고 메시지는 깨우는 용도라는
원칙을 따르면 **에코를 감수하고 Run 으로 보내는 편이 낫다.** 대신 읽는 쪽에서
`from=` 을 먼저 보고 자기 것인지 가리면 된다.

관련해서 하나 더 — `orca terminal list` 는 상대 터미널의 **프롬프트 미리보기**를 보여준다.
상대가 우편함이 아니라 자기 프롬프트에서 사용자를 기다리고 있는 경우, 우편함만 봐서는
그 상태를 알 수 없다. 상대가 조용하면 `terminal list` 로 무엇을 기다리는지 확인할 수 있다.

### 고쳤다 — 금액 입력 화면에서만 검증 신호가 꺼져 있었다 (B-3)

R2 에서 가장 중요한 발견이다. 같은 `@jisu` 를 화면별로 따라간 실측 —
대상 선택 7.88 → **금액 입력 헤더 2.56** → 확정 7.73 — 이 없었으면 못 찾았을 것이다.

원인은 화면마다 핸들 색을 따로 붙인 것이었다. 색을 `handle` textStyle 안으로 옮겨

같은 수정으로 B-2(핸들·단위 `P` 의 AA 미달)도 함께 풀렸다. 동명이인 신호는 대비가
아니라 크기(16 vs 14) · 굵기(500 vs 400) · 색상(주황 vs 회색)으로 유지된다 —
색만으로 구분하지 않으므로 색각 이상에서도 남는다.

### 고쳤다 — 자동 포커스 (R2-5 · R2-6)

키보드가 목록의 63% 를 덮어 다섯 명 중 두 명만 보인다는 실측과, 사용자의 "목록을 먼저
보고 싶었다"가 같은 곳을 가리켰다. 동명이인 묶음이 목록 아래쪽에 있으면 두 줄을 나란히
