# 원장

포인트의 흐름을 은행 원장으로 관리한다. 이 문서가 설계이고, 순서는 아래 「단계」다 —
**1 단계(계정)까지 됐고 2 단계(분개장)부터가 남았다.**

아직 원장이 아니다. `accounts (point_type_id, user_id) → balance` 라는 **바꿀 수 있는
칸**이 있고 이체가 그것을 `UPDATE` 한다. 그래서 **잔액이 틀렸는지 알 방법이 없다** —
대조할 원본이 없다.

## 층이 셋이다

회계는 이 셋을 다른 것으로 본다. 뭉개면 「원장」이라는 말이 무엇을 가리키는지 흔들린다.

| | 무엇 | 이 앱에서 |
|---|---|---|
| **분개장** | 사건을 시간순으로 적은 것. **원본** | `journal_entries` — 추가만 된다 |
| **전기** | 각 계정에 옮겨 적은 것 | `postings` — 사건당 둘 이상, 합 0 |
| **총계정원장** | 계정별로 모인 결과 | 계정 잔액 = 그 계정 전기의 합 |
| **시산표** | 차변합 = 대변합 검사 | 포인트별 전체 합 = 0 |

**분개장이 진실이고, 원장은 첫 번째 투영, 잔액은 두 번째 투영이다.** 잔액 행은 캐시이며
언제든 전기에서 재계산할 수 있어야 한다. **재계산 경로가 없으면 잔액 행을 두지 않는다.**

투영이어도 **판정에 쓸 수 있다** — 같은 트랜잭션에서 잠글 수 있기 때문이다. 쓸 수 없는
것은 **지연될 수 있는 사본**이다: 배치로 갱신되는 요약, 복제본. 되돌릴 수 없는 결정은
잠근 채 읽은 값으로만 한다(`docs/REBUILD.md` 「통계」).

## 계정

`(pointTypeId, holder)` 로 식별한다. 부호 규칙을 코드에 박지 않고 **계정 유형**이 정한다.

| 계정 | 유형 | 정상 잔액 | 음수 |
|---|---|---|---|
| **보유자 계정** — 사람마다 하나 | 부채. 은행이 보유자에게 진 것 | 대변(+) | 불가 |
| **발행 계정** — 포인트마다 하나 | 그 부채의 반대편 | 차변(−) | 그것이 정상 |

**보유자 잔액이 은행의 부채라는 것이 이 앱에 맞는다.** 포인트는 은행이 「나중에 무언가로
바꿔 주겠다」는 약속이고, 여정 12·13 이 그것을 그대로 말한다.

발행자도 보유자 계정을 갖는다. 발행하면 거기로 들어간다.

**에스크로 계정을 만들지 않는다.** 여정 13 이 「포인트가 묶인 채 결과를 기다리는 상태를
만들지 않는다」로 정했다. 구매는 은행장 계정으로 가는 평범한 이체다.

**소각 계정을 만들지 않는다.** 유통량 감소는 버렸다.

## 유통량은 두 방향에서 나온다

```
유통량 = 모든 보유자 계정의 합
       = −(발행 계정 잔액)
```

**둘이 반드시 같고, 그것이 시산표다.** 지금 `point_types.totalIssued` 는 한 칸이라 틀려도
알 수 없다.

## 분개

```
journal_entries
  public_id, kind, requester_id, idempotency_key, point_type_id, occurred_at
  unique (requester_id, idempotency_key)

postings
  journal_entry_id, account_id, amount(부호 있음), seq
```

**멱등성 키가 한 곳으로 모인다.** 지금은 `transfers` · `issues` · `cap_changes` 셋에 따로
있고 unique 제약도 셋이다.

**unique 가 하나가 되면 위반을 잡은 뒤의 갈래도 하나가 된다.** 지금 초대는 키 말고
살아 있는 초대 쪽으로도 터질 수 있어서, 잡은 뒤 키로 읽어 없으면 한 번 더 간다. 이체는
키로 터졌으면 키로 반드시 찾으므로 그 갈래가 도달하지 않는다. 사건의 키가
`journal_entries` 하나에 모이면 이체 모양만 남는다.

**회원 자격은 원장에 들어오지 않는다.** 초대·수락·나가기·내보내기는 전기를 낳지 않고
**내역에도 나오지 않는다.** 상한 변경을 전기 없는 사건으로 분개장에 넣는 것과 다르다 —
그것은 내역에 나오기 때문이다. `invites` 의 키 unique 는 원장 밖에 그대로 남는다.

사건별 전기:

| 사건 | 전기 |
|---|---|
| 이체 | `보낸이 −N` · `받는이 +N` |
| 발행 | `발행 계정 −N` · `발행자 +N` |
| 구매 | `산 사람 −N` · `은행장 +N` (교환권은 별도 기록) |
| 상한 변경 | **전기가 없다** |

**상한 변경도 같은 분개장에 넣는다 — 전기를 낳지 않는 사건으로.** 그러면 내역이 쿼리
하나가 된다. 지금은 서버가 이체 목록과 상한 변경 목록을 시간순으로 섞어 주고 있다.

**구매는 유통량을 줄이지 않는다.** 보유자끼리의 이체라 발행 계정을 건드리지 않는다.
이것이 계약과 맞는다 — `totalIssued` 는 누적이고, 은행장에게 돌아온 포인트도 발행된
것이다.

## 불변식 — 검사할 수 있다

1. **사건마다 전기 합 = 0**
2. **포인트마다 전체 전기 합 = 0** (시산표)
3. **보유자 계정 잔액 ≥ 0** — 음수는 발행 계정만
4. **−(발행 계정) ≤ `issueCap`**
5. **잔액 행 = 그 계정 전기의 합**

지금 이 중 어느 것도 검사할 수 없다.

**어디서 지키는지가 무엇을 지키는지만큼 중요하다.** 제일 위는 **길을 하나로 만드는
것**이다 — 어길 길이 없으면 지킬 것도 없다. 그 다음이 스키마다. unique 와 CHECK 는 어느
길로 들어와도 참이다. 못 막으면 **부팅이 검사하고**, 그것도 안 되면 **조용히 넘기지 말고
터지게 둔다.**

아래로 갈수록 검사가 늦다. **위로 올라가면 아래 것은 지운다** — 남겨 두면 무엇이 그
성질을 지키는지가 흐려지고, 지워도 아무것도 안 빨개지는 검사가 하나 생긴다.

**트리거는 쓰지 않는다.** binlog 가 켜진 MySQL 에서 `CREATE TRIGGER` 는 SUPER 를 요구하고,
`log_bin_trust_function_creators` 를 켜는 것으로 우회하면 **앞으로의 모든 배포가 그 플래그를
요구한다.** 불변식 하나를 위해 복제 신뢰 경계를 통째로 여는 것이라 값이 맞지 않는다.

## 원장잔액과 가용잔액

은행은 **원장잔액**과 **가용잔액**을 나눈다. 이 앱의 `Balance.amount` 와 `sendable` 이
그것이다.

**가용잔액은 원장에 없다.** 은행에서도 지급정지·미결제는 원장 밖 계산이다. 그래서 비공개
은행에서 나온 사람의 언 잔액이 원장에 흔적을 남기지 않는 것이 맞다 — 원장잔액은 그대로고
가용잔액만 0 이다. **회원 자격이 바뀌어도 원장은 바뀌지 않는다.**

## 상한은 회계가 아니라 규정이다

`issueCap` 은 분개로 표현되지 않는다. 은행의 한도와 같아서 원장 밖 규칙이 원장을 읽고
판정한다.

```
발행: 발행 계정을 잠그고 읽는다 → −잔액 + amount ≤ issueCap
```

**행 하나를 잠그면 된다.** 집계가 아니다. 지금 `findForUpdate(point_types)` 가 하는 일을
발행 계정이 받는다.

## 은행과 다르게 가는 곳 셋

**역분개가 없다.** 은행은 오기입을 반대 분개로 고친다. 이 앱은 그 경로를 사용자에게 주지
않는다.

다만 **「데이터를 고칠 수 없다」와 「사용자에게 취소가 없다」는 다르다.** 추가만 되는
원장에서는 정정도 분개이고 **그 분개가 보인다.** 지금은 잔액을 `UPDATE` 하면 흔적이 없다.
그래서 원장이 오히려 「포인트는 회수하지 않는다」를 강제한다 — **경로를 만들지 않는 것과,
만들면 반드시 보이는 것은 같이 간다.**

**마감이 없다.** 은행은 일마감으로 잔액을 스냅샷해 처음부터 재생하지 않는다. 지금 규모에서
그것은 없는 문제에 대한 방어다. 잔액 행 하나와 재계산 경로면 된다.

**거래일과 기표일을 나누지 않는다.** 확정이 곧 기입이라 `occurredAt` 하나면 된다. 예약
이체 같은 것이 오면 그때 나눈다.

## 통화를 넘지 않는다

은행에서 환전은 **분개 두 개**지 통화를 넘는 전기 하나가 아니다. 여기도 같다. 포인트 간
교환이 나중에 생기면 **사건 둘**이다.

## 원장이 해결하지 않는 것

**락 순서 문제는 남는다.** 잔액 행 둘을 만지므로 A→B 와 B→A 가 겹치면 여전히 교착할 수
있다. 정렬해서 만지는 규칙이 필요하다.

달라지는 것은 **그 규칙이 한 곳에만 있다는 점**이다. 지금은 `TransferService` 안에
`if (meId < recipientId)` 로 손으로 있다. 원장에서는 사건을 받아 전기를 적용하는 곳이
하나이므로, 구매·나눠주기가 와도 그 코드를 다시 쓰지 않는다.

**사라지는 것은 셋이다** — `ensureBalanceRow`(전기는 행을 미리 만들 필요가 없다),
`credit` 반환값 미검사(전기가 사건에 원자적으로 묶인다), 발행의 FK 공유락 순서 주석.

## 안 가져오는 것

계정번호 체계 · 배치 전기 · 손익 계정(발행비용·수익) · 다계층 계정과목. **전부 보고서를
내는 은행에 필요한 것이고 여기는 보고서를 내지 않는다.**

손익 계정을 두지 않는 것은 판단이다. 정석 포인트 회계는 발행을 「판촉비 / 포인트부채」로
잡는데 그것은 재무제표를 만들 때 필요하다. **나중에 필요해지면 발행 계정을 쪼개면 된다** —
분개장이 남아 있으므로 소급해서 다시 분류할 수 있다. 그것이 원장을 두는 이득 중 하나다.

## 정한 것 둘

**전기는 부호 하나다.** 차변·대변 칸을 나누면 「음수 금액」이 타입에서 막히지만, 계정 유형이
이미 부호를 정하고 있어(보유자 ≥ 0 · 발행 ≤ 0 이 스키마 CHECK) 칸을 나눠 얻는 것이 겹친다.

**사건에 `kind` 를 둔다.** 전기 모양에서 유추하면 화면이 원장 모양을 알아야 한다 —
「화면이 원장 규칙을 다시 계산하지 않는다」와 맞지 않는다.

## 동시에 왔을 때 — 어디서 나고 무엇이 막는가

`docs/API.md` 「동시에 왔을 때」는 **무엇이 참이어야 하는지**를 적는다. 여기는 그것이 코드
어디서 지켜지고 어디서 안 지켜지는지다. 지금(1 단계) 기준이고, 2 단계 이후가 무엇을 바꾸는지를
같이 적는다.

### 잡혀 있는 것

| 경합 | 지금 막는 것 | 확인 |
|---|---|---|
| 같은 지갑에서 동시에 둘 나감 | 조건부 `UPDATE … where balance >= :amount`, 영향 행 0 이 거절. 읽고 빼서 쓰지 않는다 | 동시성 테스트 |
| A→B 와 B→A 가 겹침 | 잔액 행을 **사용자 id 오름차순**으로 건드린다 | 동시성 테스트 |
| 발행 둘이 여유 하나를 다툼 | `point_types` 행을 `FOR UPDATE` 로 잠그고 그 안에서 상한을 본다 | 동시성 테스트 |
| 상한 낮추기와 발행이 겹침 | 같은 행을 잠근다 | 동시성 테스트 |
| 같은 키가 동시에 옴 (창설·초대·상한·수락) | unique 위반 → 롤백 → 있는 것을 돌려준다 | 동시성 테스트 |
| refresh 회전이 겹침 | 조건부 `UPDATE … where revoked_at is null`. 진 쪽은 탐지를 안 켠다 | 동시성 테스트 |

이 표의 공통점은 **읽고 판단하고 쓰는 세 문장을 한 문장으로 줄였거나, 판단 전에 행을
잠갔다**는 것이다. 2 단계 이후에도 이 둘만 쓴다.

### 잡히지 않는 것 — 2 단계가 닫아야 한다

**1. 멱등성 unique 가 쓰기의 마지막 문장이라, 경쟁에서 진 재시도가 `422 · none` 을 받는다.**
이체는 차감·입금 뒤에 `transfers` 를 넣고, 발행은 상한 검사·입금 뒤에 `issues` 를 넣는다.
같은 키가 동시에 오면 진 쪽은 **이긴 쪽이 이미 뺀 잔액**에 다시 차감을 시도하고, 잔액이 꼭
한 번치였으면 unique 에 닿기 전에 `INSUFFICIENT_BALANCE` 로 떨어진다. 발행은 `CAP_EXCEEDED`.
사용자는 「아무것도 나가지 않았어요」를 보는데 나갔다. **`outcome: none` 이 거짓말을 하는
유일한 자리다.**

닫는 법은 순서다 — **사건 행(`journal_entries`)을 첫 문장으로 넣는다.** `(requester_id,
idempotency_key)` unique 가 전기보다 먼저 터지면 진 쪽은 잔액에 닿지 않는다. 「unique 가
하나가 되면 갈래도 하나가 된다」의 실제 내용이 이것이다. 테스트는 **잔액 = 금액** ·
**여유 = 금액**에서 같은 키 동시 8 발이다 — 지금 테스트는 잔액이 넉넉해 전부 차감에 성공한
뒤 unique 에서 갈리므로 이 경우를 안 만든다.

**2. 발행자가 자기 포인트를 보내면서 동시에 발행하면 교착할 수 있다.** 이체는 잔액 행 둘을
X 로 쥔 채 `transfers` 를 넣는데, 그 삽입이 FK 검사로 `point_types` 행의 S 락을 잡는다.
발행은 `point_types` 를 X 로 쥔 채 발행자의 잔액 행에 입금한다. 발행자가 양쪽에 있으면
서로를 기다린다 — InnoDB 가 하나를 죽이고 그쪽은 `500 · unknown` 이다. 한 사람이 두 기기나
SDK 로 동시에 할 때만 나지만, **공급의 뮤텍스가 모두가 FK 로 스치는 행(`point_types`)인 것**이
원인이다.

닫는 법은 뮤텍스를 옮기는 것이다 — **발행 계정 행이 그 포인트의 공급을 잠근다.** 발행도
상한 변경도 그 행을 잠그고, `point_types` 는 아무도 X 로 잡지 않는다(상한 값 갱신은 발행
계정 락 아래에서 하는 한 문장이다). 그러면 이체는 보유자 행만, 발행은 발행 계정 → 보유자
행 순으로 잡고, **보유자 행을 쥔 채 발행 계정을 기다리는 경로가 없다.** 이것이 락 순서
규칙이고 적용부 한 곳에만 있다.

**3. 잠금 읽기가 1 차 캐시를 지나면 낡는다.** `findForUpdate` 는 락은 잡되, 그 엔티티가 같은
트랜잭션에서 이미 로드돼 있으면 **옛 값을 돌려준다.** 지금은 「잠금 조회가 첫 로드여야 한다」는
주석과 `findIdByPublicId` 우회로 지키고 있다 — 규율이지 구조가 아니다. 누가 앞에 조회 하나를
더하면 상한 판정이 조용히 낡은 값으로 돈다.

닫는 법: **잠금 읽기는 엔티티가 아니라 값을 읽는다.** `select balance … for update` 처럼
스칼라로 읽으면 영속성 컨텍스트를 지나지 않아 낡을 수 없다. 또는 잔액과 같은 모양으로 —
판정을 `UPDATE … where` 조건에 넣고 영향 행 수로 본다. 둘 중 무엇이든 적용부 한 곳에서만
쓴다.

**4. 권한 판정 전에 계정 행이 생긴다.** 발행 경로가 `ensureAccount` 를 `NOT_ISSUER` 앞에서
별도 트랜잭션으로 하므로 거절돼도 남는다 — 아무나 `POST /issues` 에 남의 은행 id 를 넣으면
그 은행에 자기 잔액 0 행이 생긴다. 지금은 `balance > 0` 이 거르지만 「행의 존재」가 관계의
신호가 되는 날 샌다. 2 단계에서 **행을 미리 만들지 않으면** 사라진다 — 입금은
`insert … on duplicate key update balance = balance + :n` 한 문장이다.

### 막지 않고 받아들이는 것

- **이체 도중 보낸 사람이 내보내지는 것.** `isMember` 를 읽고 차감하는 사이에 내보내기가
  끼면 이체는 성사된다. 회원끼리의 이체 한 건이 내보내기 직전에 일어난 것이고 돈이 새는
  것이 아니다. 회원 자격은 원장 밖이라 잠그지 않는다
- **앱 시계.** `occurred_at` 은 앱의 `Instant.now()` 다. 인스턴스가 하나라 순서가 흔들리지
  않는다. 여럿이 되는 날 DB 시각으로 옮긴다 — 그때까지는 같은 마이크로초의 순서는 id 가 가른다
- **락 대기 시간 초과.** 발행 계정을 오래 쥔 트랜잭션이 있으면 그 은행의 발행이 50 초
  기다렸다가 `500 · unknown` 으로 떨어진다. 지금 규모에서는 관측만 한다 — 트랜잭션 시간 제한은
  5 단계에서 숫자를 정한다

### 교착·락 패배·커넥션 획득 실패는 `unknown` 이 아니다

InnoDB 가 교착을 풀려고 죽인 쪽, 락 대기에서 진 쪽, 풀에서 커넥션을 못 얻은 쪽은 **트랜잭션이
통째로 롤백됐거나 시작도 못 한 것**이라 서버는 아무것도 하지 않았다는 것을 안다. 지금은
`Throwable` 로 떨어져 `500 · unknown` 인데, 그러면 화면이 「확인하기」로 가고 사용자는 돈의
위치를 의심한다. **`SERVER · outcome: none`** 으로 답한다 — 같은 키로 다시 보내면 된다.

잡는 타입은 `PessimisticLockingFailureException` 이다 — 리뷰가 실측했다. 교착으로 죽은 쪽에
도착하는 것은 `DeadlockLoserDataAccessException` 이 아니라 `CannotAcquireLockException` 이고,
둘 다 저 부모 아래다. 자식 하나만 잡으면 실제로 오는 쪽을 놓친다. 커넥션 획득 실패는
`CannotGetJdbcConnectionException`. 5 단계.

「잡히지 않는 것 2」의 교착은 리뷰가 40 라운드에서 2 번 재현했다 — **5 %다. 드물다고 적지
않는다.**

셋째가 있다 — **`deleteById` 는 읽고 지우는 두 문장이라, 동시에 지우면 진 쪽이 없는 행에
`DELETE` 를 날려 `ObjectOptimisticLockingFailureException` 으로 `500 · unknown` 이 된다.**
리뷰가 나가기 동시 8 발로 재현했다(1×204 · 7×500). 이것은 접을 것이 아니라 **경로를 없앨
것**이다 — `delete … where` 한 문장이면 0 행은 그냥 0 행이고, 답은 `204` 다. 그 사람이 원한
것은 이미 참이다. 「읽고 판단하고 쓰는 세 문장을 한 문장으로」가 아직 안 닿은 자리였다.

## 커넥션

풀은 Hikari 기본 10 이고 설정에 없다. **`REQUIRES_NEW` 는 바깥 트랜잭션이 커넥션 하나를 쥔
채 하나를 더 꺼낸다.** 동시 요청이 풀 크기에 닿으면 전부가 두 번째를 기다리며 서로를 막고,
30 초 뒤 `connectionTimeout` 으로 한꺼번에 `500 · unknown` 이다 — 기울기가 아니라 절벽이다.
지금 셋이 그렇다.

| 어디 | 왜 있나 | 2 단계 이후 |
|---|---|---|
| 잔액 행 생성 (이체·발행) | 중복키가 바깥 트랜잭션을 rollback-only 로 오염시키지 않게 | **없앤다.** 행을 미리 만들지 않는다 — 입금이 upsert 한 문장 |
| 상한 변경의 멱등 재조회 | REPEATABLE READ 스냅샷이 잠금 전에 고정돼 이긴 쪽의 커밋이 안 보여서 | **없앤다.** 사건 행이 첫 문장이면 unique 가 먼저 갈리고 재조회는 컨트롤러가 트랜잭션 밖에서 한다 |
| refresh 재사용 탐지의 사슬 무효화 | 탐지 예외가 바깥을 롤백시켜도 무효화는 남아야 해서 | 남긴다. 드물고, 이쪽은 돈이 아니다 |

규칙으로 적는다 — **요청 경로에서 `REQUIRES_NEW` 를 쓰지 않는다.** 2 단계가 여는 `server/`
규율 검사 자리에서 그 어노테이션을 센다(허용 목록은 위 마지막 줄 하나). 그리고 풀 크기를
설정에 명시하고 actuator 의 `hikaricp.connections.pending` 을 본다 — 0 이 아닌 순간이 절벽
앞이다.

`findAll()` 뒤 메모리 필터(지갑·내역·은행 목록·사용자 검색)는 커넥션을 오래 쥐는 쪽이다.
은행이 수백이 되기 전에 관계 집합으로 `where … in` 을 건다. 4 단계.

## 무엇이 뿌리이고 무엇이 패치인가

위 「잡히지 않는 것」 넷과 `REQUIRES_NEW` 셋 중 둘은 **서로 다른 문제가 아니다.** 전부 한 선택에서
갈라져 나온 가지이고, 지금까지 고친 것은 그 가지를 하나씩 덮은 것이다.

**뿌리 — 쓰기의 단위가 「사건」이 아니라 「칸」이다.** 이체는 잔액 칸을 `UPDATE` 하고, 사건은
표마다 자기 키를 갖고, 공급의 뮤텍스는 모두가 FK 로 스치는 은행 행이다. 거기서 제약 셋이
따라온다 — **칸은 미리 있어야 한다 · 키는 표마다다 · 뮤텍스는 `point_types` 다.** 패치는 전부
이 셋 중 하나를 덮는다.

| 패치 | 덮은 제약 | 덮다가 생긴 것 | 지우는 단계 |
|---|---|---|---|
| `ensureAccount` + `AccountInitializer`(REQUIRES_NEW) | 칸은 미리 있어야 한다 | 커넥션 절벽(실측: 풀 2 · 8 발 전부 30 초 뒤 500) · 권한 판정 전에 행이 남는다 | 2·3 |
| `IssueService` 의 「잔액 행 생성이 잠금보다 먼저」 주석 | 같은 것 | 순서 규율 하나 — 어기면 FK 락으로 스스로와 교착 | 2 |
| `pointTypeIdsHeldBy` 의 `balance > 0` | 같은 것 — 거절된 이체가 남긴 0 행을 거르려고 | **「가졌던 0」이 공개 은행에서 지갑에서 사라진다.** 다 쓴 공개 포인트는 회원도 발행자도 아니라 카드가 없다. 여정 1 「가진 것과 가졌던 것은 다르다」가 공개 은행에서는 성립하지 않는다 | 3 — 행이 사건에서만 나게 되면 `HOLDS_BALANCE` 를 「받은 적 있다」(행의 존재)로 바꿀 수 있다. 계약 결정이고 조율이 한다 |
| 컨트롤러의 「unique 위반 → 다시 읽어 돌려준다」 ×5 | 키는 표마다다 — 멱등 판정이 마지막 문장 | 진 재시도가 `422 · none`(실측: 1×201 · 7×422, 그 뒤 by-key 는 이체를 돌려준다 — **서버가 답을 쥔 채 안 나갔다고 말한다**) | 2·3 — 사건 행이 첫 문장이면 이 catch 는 패치가 아니라 **유일한 갈림길**이 된다. 남되 다섯이 하나로 모인다 |
| `CapChangeLookup`(REQUIRES_NEW) | 같은 것 — 멱등 판정이 잠금 뒤라 스냅샷이 낡아서 | 커넥션 하나 더 | 4 |
| 초대 컨트롤러의 catch 안 재시도 | 같은 것 — unique 둘 | — | 남는다. 회원 자격은 원장 밖이다 |
| `findIdByPublicId` + 「잠금 조회가 첫 로드여야 한다」 | 뮤텍스는 `point_types` 다 — 엔티티를 잠금 조회하므로 | 1 차 캐시 낡음을 규율로 막는다 | 2 — 잠금 읽기를 값으로 |
| (패치 없음) | 같은 것 | 발행자의 자기 이체 ∥ 발행 교착 5 % | 2 — 뮤텍스를 발행 계정 행으로 |

**그래서 지금 문제는 근본적이지 않다.** 도메인이 요구하는 것(멱등성 키 · A→B/B→A 순서 ·
공급에 뮤텍스가 하나 · REPEATABLE READ 에서 실패한 트랜잭션 밖에서 다시 읽기)은 전부 원장
으로 가도 그대로 남고 이미 맞게 돼 있다. 문제는 **사건을 기록하지 않은 채 사건의 성질을
흉내내느라 쌓인 가지**다.

**근본 해결의 기준은 하나다 — 패치가 지워지는가.** 2·3 단계 PR 이 위 표의 「지우는 단계」
칸대로 실제로 지우지 못하면 그것은 원장 위에 패치를 한 겹 더 얹은 것이다. 완료 기준에
**지운 것 목록**이 들어가는 이유다. 남는 것은 셋뿐이어야 한다 — refresh 의 `REQUIRES_NEW`
(돈이 아니다), 초대의 재시도(원장 밖), 그리고 unique 위반을 받아 돌려주는 갈림길 하나.

`findAll()` 뒤 메모리 필터 넷과 `@Transactional` 이 컨트롤러에 붙은 것은 이 뿌리와 무관하다 —
취향이고 4 단계에서 걷는다.

## 단계

각 단계가 **닫는 것**을 적는다. 닫는 것이 없으면 단계가 아니다. **SDK 는 하지 않는다** —
여정 「나중」 3 은 범위 밖이고, 기계의 멱등성이 값을 할 자리였지만 그 값을 받을 바깥이 없다.

| 단계 | 무엇 | 닫는 것 | 상태 |
|---|---|---|---|
| **1** | `balances` → `accounts`. 발행 계정이 창설과 함께 난다 | 발행 계정이 둘 생기는 것(스키마 unique) · 계정 없는 포인트(부팅 검사 → 길 하나) | 끝 |
| **2** | `journal_entries` · `postings` · **적용부 하나**. 첫 호출부는 발행 | 위 「잡히지 않는 것」 1·2·3·4 **전부** · `REQUIRES_NEW` 둘 · 불변식 1~5 가 검사 가능 | 진행 중 |
| **3** | 이체가 적용부를 지난다. `ensureAccount` 와 `AccountInitializer` 가 사라진다. `HOLDS_BALANCE` 를 「받은 적 있다」로 바꿀지 정한다 | 이체의 같은 키 경합 · 커넥션 절벽(요청 경로) · 락 순서가 한 곳 · 공개 은행의 「가졌던 0」 | |
| **4** | 상한 변경이 전기 없는 사건으로 분개장에 든다. 내역이 쿼리 하나(`occurred_at, id` 커서). `cap_changes` 의 키가 사건으로 모인다 | 세 목록을 합치는 내역 · 멱등성 unique 셋 · `findAll()` 필터 | |
| **5** | 재계산과 대사. `accounts.balance` 를 전기에서 다시 만드는 경로 · 부팅·주기 검사 · 교착·락 패배 → `none` · 트랜잭션 시간 제한 · 풀 크기와 지표 | 「잔액이 틀렸는지 알 방법이 없다」 · `unknown` 의 과잉 | |
| **6** | 상점. 구매 = 산 사람 −N · 은행장 +N 의 평범한 이체 + 교환권 기록. 재고·1 인 한도는 잠그고 읽는다 | 여정 12·13 의 되돌릴 수 없는 것 | |

**2 단계의 시작 조건** — 리뷰에서 나온 것이라 여기 못 박는다.

1. 사건 행 삽입이 **첫 문장**이다. 멱등성 unique 위반이 전기보다 먼저 난다
2. 공급의 뮤텍스는 **발행 계정 행**이다. 발행·상한 변경이 그것을 잠그고 `point_types` 는
   아무도 X 로 잡지 않는다. 락 순서: 발행 계정 → 보유자 계정(id 오름차순). 적용부 한 곳
3. 잠금 읽기는 **값**으로 한다(스칼라 `for update`) 또는 조건부 `UPDATE` 다. 엔티티를 잠금
   조회하지 않는다
4. 행을 미리 만들지 않는다. 입금은 upsert 한 문장, 차감은 조건부 `UPDATE` 한 문장
5. `point_types.total_issued` 는 **지우거나**, 남기면 불변식 검사에 `= −발행 계정 잔액` 을
   넣는다. 둘 다 남기고 검사가 없으면 불변식 5 가 조용히 깨질 자리다
6. 불변식 1~5 를 **모든 테스트 끝에** 돌리는 검사가 첫 PR 에 같이 온다. 픽스처·`LedgerReset` 은
   `accounts` · `postings` 에 직접 쓰지 않는다 — 적용부를 지난다
7. 전기가 사건의 포인트를 넘지 못하는 것을 **스키마가 안다.** `postings` 에 `point_type_id`
   를 내리고 복합 FK 를 **둘** 건다 — `(account_id, point_type_id) → accounts(id, point_type_id)`
   와 `(journal_entry_id, point_type_id) → journal_entries(id, point_type_id)`. 계정 쪽만 걸면
   「전기의 포인트 = 계정의 포인트」뿐이고, 둘이면 전이적으로 **계정의 포인트 = 사건의
   포인트**가 닫힌다. 이 FK 가 S 락을 잡는 행은 이 트랜잭션이 이미 X 로 쥔 계정 행과 방금
   자기가 넣은 사건 행이라 새 교착 경로가 아니다. 트리거를 안 쓰기로 했으니 남는 스키마
   방어는 이것뿐이다
8. 테스트 — 잔액 = 금액 · 여유 = 금액에서 같은 키 동시 8 발. 그리고 풀을 2 로 줄인 채 동시
   8 발(절벽이 요청 경로에 없다는 증거)
9. 2 단계 범위는 **발행·이체**다. 상한 변경은 4 단계 — `kind` enum 에 `CAP_CHANGE` 는 그때
   끝에 더한다(MySQL 에서 enum 끝에 더하는 것은 메타데이터 변경뿐이다)
