# API 계약

계약은 **HTTP** 다. TypeScript 인터페이스가 아니다.

1차 구현에서는 `PointApi` 라는 TS 인터페이스를 계약이라 부르고 Mock 을 로컬 모듈로 두었다.
그러면 앱이 HTTP 를 한 번도 쓰지 않은 채 완성된다 — 멱등성 키가 헤더가 아니라 JS 객체
필드였고, "네트워크 실패"는 진짜 실패가 아니라 로컬에서 던진 예외였다. 실서버를 붙이는 날
클라이언트 계층을 처음부터 새로 써야 했을 것이다.

지금은 앱이 실제 `fetch` 를 하고 개발 중에는 **MSW** 가 그것을 가로챈다.
Spring Boot 가 오면 `src/mocks/` 만 지운다.

- 클라이언트: `src/api/http.ts`, `src/api/endpoints.ts`
- Mock 서버: `src/mocks/handlers.ts`, `src/mocks/ledger.ts`
- 시뮬레이션: `src/mocks/sim.ts`

기준 경로는 `/api` 다.

## 설계 결정

### 멱등성 키는 헤더다

```
POST /api/transfers
Idempotency-Key: 3a729bd1-8d12-4837-8082-97942afa0ed2
```

본문 필드로 보내면 서버가 본문을 파싱해야 키를 알 수 있고, 그러면 재시도 판정이 본문
스키마에 묶인다. 결제 API 들이 헤더를 쓰는 이유가 이것이다.

**키 없는 쓰기는 400 으로 거절한다.** 받아 주면 클라이언트가 키를 빼먹었을 때 조용히
이중 이체가 가능해지고, 그건 배포된 뒤에 발견된다.

같은 키로 다시 요청하면 새 이체를 만들지 않고 기존 것을 `200` 으로 돌려준다.

### 취소가 없다

`cancelableUntil`, `POST /transfers/:id/cancel`, `NOT_CANCELLABLE`, `cancelled` 상태가
모두 사라졌다. 이유는 `JOURNEY.md` 의 "버린 것" 에 있다 — 거의 쓰이지 않으면서 모든
이체에 인지 부하를 더하고, "몇 초 안에 결정" 자체가 스트레스다.

그래서 **쓰기는 동기·원자적**이다. 검증과 반영이 한 순간에 일어나고 응답은 확정된
이체이거나 오류다. 중간 상태가 없다는 것은 화면이 그릴 중간 상태도 없다는 뜻이다.

`Transfer` 에 `status` 필드가 없는 것도 같은 이유다. 저장된 이체는 언제나 확정된 것이다.
시스템이 만들어 낼 수 없는 값을 타입에 두면 화면은 그 상태를 그리게 되고, 그 화면은
영원히 검증되지 않는다.

**실패는 기록이 아니라 응답이다.** 실패한 요청은 내역에 남지 않는다.

### 포인트는 여럿이다

발행자마다 자기 포인트가 있고 사용자는 여러 종류를 동시에 가진다.

- 잔액은 `(pointTypeId, userId)` 단위다
- 이체는 **같은 종류끼리만** 일어난다. 요청에 `pointTypeId` 가 없으면 400
- 발행은 `PointType.issuerId` 와 요청자가 같을 때만 성공한다 (403 `NOT_ISSUER`)
- 최근 대상은 **포인트별로** 다르다

### 발행은 이체와 같은 모양이다

`POST /issues` 는 `POST /transfers` 와 같은 본문·같은 헤더를 받고 같은 `Transfer` 를
돌려준다. 다른 것은 `fromId` 가 `null` 이고(무에서 만든다) `totalIssued` 가 늘어난다는 점뿐이다.
클라이언트가 두 흐름을 하나의 상태 기계로 다룰 수 있는 이유다.

### 인증

모든 읽기·쓰기가 토큰을 통과한다. 화면마다 확인하면 한 곳이 빠지고, 빠진 곳이 남의
잔액을 보여준다.

```
Authorization: Bearer <token>
```

| 메서드 | 경로 | 설명 |
|---|---|---|
| `POST` | `/api/auth/login` | `{ handle, password }` → `{ accessToken, refreshToken, user }` |
| `POST` | `/api/auth/refresh` | `{ refreshToken }` → `{ accessToken, refreshToken }` |
| `POST` | `/api/auth/logout` | `{ refreshToken }` → `204`. 그 사슬 전체 무효 |

**Access + Refresh 하이브리드다.** access 는 짧고(15분) refresh 는 길다(14일).
되돌릴 수 없는 송금을 다루므로 access 를 길게 두지 않는다.

**refresh 는 회전한다.** 갱신하면 옛 refresh 는 즉시 죽는다. 이미 회전된 것이 다시
오면 훔친 것일 수 있으므로 **그 사슬 전체를 무효화**한다 — 도둑과 주인 중 누가 먼저
왔는지 알 수 없으니 둘 다 끊는 것이 안전하다.

클라이언트는 `401` 을 받으면 **한 번 갱신하고 원요청을 다시 보낸다.** 멱등성 키가
헤더에 있어서 이 재시도가 안전하다 — 키를 처음부터 헤더로 둔 값이 여기서 난다.
갱신은 한 번에 하나만 돈다. 여럿이 동시에 갱신하면 회전 때문에 뒤엣것들이 재사용으로
탐지돼 세션이 통째로 죽는다.

토큰이 없거나 죽었으면 `401` + `{ "code": "UNAUTHENTICATED" }`,
자격증명이 틀리면 `401` + `{ "code": "BAD_CREDENTIALS" }` 다.
**어느 핸들이 존재하는지 알려주지 않는다** — 두 경우의 화면 문구가 같다.

**핸들 표기는 서버가 정규화한다.** 앞의 `@` 를 떼고 소문자로 맞춘 뒤 비교하므로
`@minho` · `minho` · `MINHO` 가 모두 같은 사람이다. 클라이언트는 입력을 그대로 보낸다 —
양쪽이 정규화하면 곧 한쪽이 달라진다. "@ 를 빠뜨렸어요" 라고 알려 주는 길은 만들지
않는다. 그것이 곧 존재하는 핸들을 알려 주는 길이다.

**서버는 refresh 를 본문으로 받는다. 누가 그것을 보관하는지는 계약이 아니다.**

`HttpOnly` 쿠키를 검토했다가 버렸다. WebView 에서 쿠키가 실용적이려면 same-site 여야
하고, 그러려면 정적 파일과 API 가 같은 오리진 — 프록시가 전제가 된다. 프록시 없이
`SameSite=None` 으로 가면 iOS WKWebView 의 ITP 가 상호작용 없는 cross-site 쿠키를 며칠
안에 지우고 Android WebView 도 같은 방향이다. **사용자가 이유를 알 수 없이 로그아웃된다** —
되돌릴 수 없는 송금을 다루는 앱에서 가장 나쁜 자리에 불신이 생긴다. 프록시를 전제하면
아직 정하지도 않은 배포 형태가 거기 묶인다.

대신 보관 주체를 옮긴다. 지금은 웹이 메모리에 들고(새로고침하면 다시 로그인하는 것이
그 대가다), RN 셸이 서면 셸이 네이티브 보안 저장소에 refresh 를 갖고 WebView 에는 15분짜리
access 만 둔다. 갱신은 브릿지로 셸에 요청한다. `HttpOnly` 가 주려던 것 — XSS 가 장기
토큰을 훔치지 못한다 — 을 그대로 주면서 쿠키·SameSite·ITP·프록시를 전부 우회한다.
서버 계약은 그때도 바뀌지 않는다.

`localStorage` 에는 두지 않는다. XSS 한 번에 샌다.

## 엔드포인트

| 메서드 | 경로 | 응답 | 설명 |
|---|---|---|---|
| `GET` | `/api/me` | `User` | 현재 사용자 |
| `GET` | `/api/wallet` | `Wallet` | 포인트별 잔액 전부 |
| `GET` | `/api/point-types` | `PointType[]` | 존재하는 포인트 종류 |
| `GET` | `/api/users?q=&pointTypeId=` | `User[]` | 검색. 비공개 은행이면 회원만 |
| `GET` | `/api/recent?pointTypeId=&limit=` | `User[]` | 그 포인트로 최근에 보낸 사람 |
| `POST` | `/api/transfers` | `Transfer` `201` | 이체. `Idempotency-Key` 필수 |
| `POST` | `/api/issues` | `Transfer` `201` | 발행. 발행자만. **대상 없음** |
| `POST` | `/api/point-types` | `PointType` `201` | 포인트 창설. `Idempotency-Key` 필수 |
| `PATCH` | `/api/point-types/:id/cap` | `PointType` | 상한 변경. 발행자만. `Idempotency-Key` 필수 |
| `GET` | `/api/transfers/:id` | `Transfer` | 단건. **404 는 일어나지 않았다는 뜻** |
| `GET` | `/api/transfers/by-key?idempotencyKey=` | `Transfer \| null` | 결과를 모를 때의 확인 |
| `GET` | `/api/history?pointTypeId=&limit=` | `HistoryEntry[]` | 내역, 최신순. 이체와 상한 변경이 섞인다 |

이체 본문:

```json
{ "pointTypeId": "pt_on", "toId": "u_jisoo", "amount": 30000 }
```

발행 본문 — **`toId` 를 받지 않는다.** 발행은 자기 지갑으로만 들어간다
(`docs/JOURNEY.md` 여정 7). 대상이 실려 오면 `400` 이다. 조용히 무시하면 발행과
이체가 같은 흐름에서 섞이고, 발행자는 잘못 고른 것을 알 방법이 없다.

```json
{ "pointTypeId": "pt_gm", "amount": 100000 }
```

**`amount` 는 안전 범위의 양의 정수만 받는다.** 소수점이 실려 오면 `400` 이다.
타입은 컴파일 시점만 지키고 HTTP 경계에는 타입이 없다 — 통과시키면 잔액에 소수가
생기고, 화면의 한글 병기가 그 소수를 조용히 버려 숫자와 한글이 서로 다른 값을 말한다.
여정 4 의 병기는 숫자가 감추는 것을 한글이 드러내라고 있는 장치인데, 거기서 거꾸로
돈다. 키패드로는 소수점을 칠 수 없으므로 **이 구멍은 화면 QA 로 잡히지 않는다.**

**`toId` 가 요청자 자신이면 `400` 이다** (이체만. 발행은 원래 자기 지갑으로 들어간다).
근거: `docs/JOURNEY.md` 「버린 것」. `GET /api/users` 도 요청자를 결과에서 뺀다.

포인트 창설 본문:

```json
{ "name": "동네빵집", "emoji": "🍞", "accent": "orange", "issueCap": 1000000,
  "visibility": "public", "description": "골목 끝 빵집이에요. 빵 사면 쌓여요." }
```

**누구나 만들 수 있고 상한도 자기가 정한다** (`docs/JOURNEY.md` 여정 9). 서버는 발행자
자격을 심사하지 않는다. 대신 다음을 지킨다.

| 필드 | 제약 | 어긴 응답 |
|---|---|---|
| `name` | 공백 제외 1~12자 | `400` |
| `emoji` | 허용 목록 안의 이모지 하나. **겹쳐도 된다** | `400` |
| `accent` | `PointAccent` 중 하나 | `400` |
| `description` | 공백 제외 0~60자. 없어도 만들 수 있다 | `400` |
| `issueCap` | 안전 범위의 양의 정수 | `400` |
| `visibility` | `"public"` 또는 `"private"`. **기본값이 없고 나중에 바꿀 수 없다** | 없으면 `400` |

**`visibility` 에 기본값을 두지 않는다.** 서버는 빠진 요청을 `400` 으로 거절하고,
화면은 만드는 사람에게 묻는다 — 미리 골라 둔 쪽 없이. 바꿀 수 없는 값에 기본값을 두는
것은 **만든 사람이 고른 적 없는 상태를 영구히 고정하는 일**이다. 「기본이 공개」면
비공개로 두려던 은행이 조용히 열린 채로 남고, 되돌릴 길이 없다.

초대와 회원이 아직 서지 않았다는 것은 미루는 이유가 되지 않는다. 지금 만든 은행도
`visibility` 는 지금 정해져 영원히 남는다.

만든 사람이 발행자다 — 본문에 `issuerId` 를 받지 않는다. 응답의 `totalIssued` 는 0,
`canIssue` 는 참이다. **지우는 엔드포인트는 없다.** 누군가 한 번이라도 받은 포인트를
지우는 것은 남의 지갑을 지우는 일이고, "아직 아무도 안 가졌으면 지울 수 있다" 로 두면
지울 수 없게 되는 순간을 사용자가 예측하지 못한다.

**표식은 이모지고, 유일하지 않다.** 두 글자 약어(`BK`)는 만든 사람이 읽는 표식이지
받는 사람이 읽는 표식이 아니다 — 좁은 자리에서 알아보라고 둔 것인데 정작 알아볼 수가
없다. 이모지는 그 자리에서 읽힌다.

유일성은 함께 버린다. **쓸 만한 이모지는 몇백 개뿐이라 유일하게 두면 먼저 만든 사람이
차지하는 경주가 된다** — 빵집 백 번째는 빵을 못 쓴다. 그리고 유일성은 애초에 사칭을
막지 못했다. 그 일은 발행자 핸들과 만든 날이 한다(여정 10).

**그래서 이모지로 무엇을 가르지 않는다.** 이모지는 알아보는 표식이지 가리키는 표식이
아니다. 같은 이름이 겹칠 때 붙는 것은 이모지가 아니라 발행자다(`nameIsShared`).
확정 화면도 마찬가지다 — 이모지가 같아도 다른 은행일 수 있다.

**서버는 허용 목록 안의 값만 받는다.** 이모지는 한 글자처럼 보이지만 결합된 여러
코드포인트일 수 있고(피부색·ZWJ·이형 선택자), 그러면 길이 검사·너비·폰트 대체가 기기마다
갈린다. 목록으로 두면 **모든 기기에서 같게 보이는 것만** 고르게 된다. 국기는 넣지
않는다 — 무엇을 목록에 넣을지가 정치적 판단이 된다.

`409 SYMBOL_TAKEN` 은 사라진다.

**설명은 발행자가 적고, 바꿀 수 있다.** 상한과 다르다 — 상한은 보유자에게 하는 약속이라
되돌릴 수 없지만, 설명은 약속이 아니라 소개다. 이력에도 남기지 않는다.

**설명이 사실보다 위에 놓이지 않는다.** 여기는 「공식 계정입니다」라고 적을 수 있는
자리다. 앱은 그것을 판정하지 않는다(여정 10) — 대신 판단 근거인 사실(발행자 핸들 ·
만든 날 · 상한 · 유통량)이 설명보다 먼저 읽히게 화면이 정한다. **발행자가 쓴 글이
앱이 보증한 글처럼 보이면 안 된다.**

상한 변경 본문:

```json
{ "issueCap": 2000000 }
```

발행자만 바꿀 수 있고(`403 NOT_ISSUER`), **이미 발행한 양보다 낮출 수 없다**
(`422 CAP_BELOW_ISSUED`). 그 아래로 내리면 유통량이 상한을 넘은 상태가 되어 상한이 뜻을
잃는다. 값이 지금과 같으면 `400` 이다 — 이력에 남는 사건이므로 아무것도 바꾸지 않는 줄을
만들지 않는다. `Idempotency-Key` 가 필요한 이유는 창설과 같다: 응답을 못 받고 다시 눌러도
이력에 두 줄이 생기면 안 된다.

**취소 엔드포인트는 없다.** 낮추는 것은 다시 `PATCH` 지만 그것은 취소가 아니다 — 올려 둔
동안 발행된 것은 이미 남의 지갑에 있다.

**멱등성 검사가 「같은 값」 검사보다 먼저다.** 순서를 뒤집으면 성공한 요청이 실패로
돌아온다 — 서버가 상한을 바꾸고 응답이 유실되면, 사용자가 같은 키로 다시 누를 때 상한은
이미 새 값이라 「지금과 같은 값」에 걸려 `400` 이 된다. **이미 일어난 일을 안 일어났다고
말하는 것**이고, 화면은 그것을 보고 바뀌지 않았다고 판단한다. 키가 먼저 답해야 한다:
같은 키가 이미 있으면 그때의 결과를 그대로 돌려준다.

같은 함정이 창설에도 있다. 응답을 못 받고 다시 누르면 기호가 이미 쓰이고 있으므로
`SYMBOL_TAKEN` 이 된다 — 자기가 방금 만든 것에 걸린다. 키를 먼저 본다.

### 흉내낼 수 없는 것 (여정 10)

누구나 포인트를 만들 수 있게 되면서 **발행자가 정하는 것은 전부 사칭 도구**가 됐다 —
이름도 기호도 색도. 그래서 응답은 **발행자가 정할 수 없는 것**을 함께 싣는다.

- `issuerHandle` — 핸들은 유일하다. `issuerName` 은 겹칠 수 있고 그것이 사칭의 통로다
- `createdAt` — 어제 만든 것과 1년 된 것은 다르다
- `totalIssued` — 여정 8 이 "보유자에게 유통량은 소음" 이라 한 것은 **이미 쓰는 포인트**의
  이야기다. 처음 만나는 순간에는 아무도 안 가진 것과 널리 도는 것이 판단을 가른다
- `nameIsShared` — 같은 이름이 원장에 또 있는가. 처음 만나는 순간이 이 값이 가장 중요한
  자리다

**서버는 진짜인지 가짜인지 판정하지 않는다.** 판정할 수 없다 — 동명이인을 가르지 못해
나란히 놓고 사람이 고르게 한 것과 같다. 사실을 모아 주고 판단은 사람이 한다.

**판단의 근거는 `issuerHandle` 이다.** 이름은 겹칠 수 있고 기호도 색도 발행자가 고르는
것이지만 핸들은 하나뿐이다. 사람을 가를 때 쓰는 것과 같은 것으로 은행도 가른다.

**별도의 확인 단계는 두지 않는다.** 비공개 은행에서는 초대 수락이 곧 확인이고, 공개
은행에서는 `neverSpent` 가 저절로 답한다 — **그 포인트를 처음 쓰면 꺼진다.** 「봤어요」를
누르게 하면 읽지 않고 눌린다.

`neverSpent` 를 서버가 판정하는 이유는 기기마다 다르면 안 되기 때문이다. 클라이언트가
기억하면 폰에서 확인한 것이 태블릿에서는 처음이 된다.

### 내역은 이체만이 아니다

`GET /api/history` 는 두 종류를 시간순으로 섞어서 준다.

```ts
type HistoryEntry =
  | { type: 'transfer'; transfer: Transfer }
  | { type: 'capChange'; capChange: CapChange }

interface CapChange {
  id: string
  idempotencyKey: string
  pointTypeId: PointTypeId
  /** 바꾼 사람. 그 포인트의 발행자다 */
  byId: UserId
  previousCap: Points
  issueCap: Points
  changedAt: string
}
```

**이체에는 상대가 실려 온다.** `Transfer.counterparty` 는 `{ name, handle, nameIsShared }`
이고, **발행이면 `null` 이다.**

클라이언트가 `toId` 로 사용자 목록을 뒤져 이름을 맞추면 안 된다. 목록에 없는 순간
조용히 틀리고, 폴백이 무엇이든 그것은 거짓말이 된다 — 실제로 「못 찾으면 나」로 떨어져
있었고, 그래서 남에게 보낸 이체가 자기에게 보낸 것처럼 보였다. `PointType.issuerName` 을
서버가 싣는 이유와 같다: **누구인지는 원장의 성질이다.**

`nameIsShared` 가 함께 오는 이유도 같다. 내역에서 「지수에게 30,000」을 보는 사람은
그 지수가 누구인지 물을 수 있어야 하고, 겹치는지는 받은 목록 안에서 셀 수 없다.

**발행에 상대를 넣지 않는다.** 발행은 대상이 없다 — 자기 지갑으로 들어간다. 빈 자리를
「나」로 메우면 **일어나지 않은 이체가 일어난 것처럼 읽힌다.** 발행 · 이체 · 상한 변경은
내역에서 서로 다른 모양이어야 하고, 위계를 빌려 쓰면 셋이 한 종류로 읽힌다.

**`idempotencyKey` 는 화면에 내보내지 않는다.** 그것은 클라이언트가 재시도를 가르려고
만든 표이지 사람이 읽을 것이 아니고, **요청자별로만 뜻이 있어서** 남에게 말해도 아무도
찾지 못한다. 사람이 가리킬 번호가 필요하면 `Transfer.id` 다.

**서버가 섞어서 준다.** 두 목록을 클라이언트가 받아 시간순으로 합치면 페이지네이션에서
깨진다 — 각 목록의 `limit` 안에 든 것만 합쳐지므로 경계에서 항목이 사라진다.

**누가 보는가.** 이체는 관여한 사람만(아래). 상한 변경은 **그 포인트가 자기 지갑에 있는
사람**과 발행자다 — `GET /api/wallet` 에 나오는 포인트면 그 포인트의 상한 변경이 내역에
보인다. 발행자만 아는 변경은 약속이 아니다 (`docs/JOURNEY.md` 여정 8).

### 회원 자격 (여정 10)

**공개 은행에는 회원이 없다.** 누구나 받고 보내고 산다. 관문이 없는데 통과 기록을 두면
그것은 공개가 아니다. 아래는 전부 `visibility: "private"` 인 은행의 이야기다.

| 메서드 | 경로 | 응답 | 설명 |
|---|---|---|---|
| `GET` | `/api/point-types/:id` | `PointType` | 은행 페이지. 보는 사람에 따라 필드가 는다 |
| `GET` | `/api/point-types/:id/members` | `User[]` | 회원 목록. 회원만 |
| `POST` | `/api/point-types/:id/invites` | `Invite` `201` | 초대. 은행장만. `Idempotency-Key` 필수 |
| `GET` | `/api/invites` | `Invite[]` | 내가 받은 초대 |
| `POST` | `/api/invites/:id/accept` | `PointType` | 수락하면 회원이 된다 |
| `DELETE` | `/api/point-types/:id/members/me` | `204` | 나간다 |
| `DELETE` | `/api/point-types/:id/members/:userId` | `204` | 내보낸다. 은행장만 |

```ts
interface Invite {
  id: string
  pointType: PointType   // 받는 사람이 판단할 것이 여기 다 있다
  /** 초대한 사람. 은행장이다 */
  byId: UserId
  byHandle: string
  createdAt: string
}
```

**비공개 은행은 초대 없이 닿을 수 없다.** 회원도 초대받은 사람도 아니면
`GET /api/point-types/:id` 가 **`404`** 다 — `403` 은 "그 은행은 존재한다" 를 알려 주는
셈이고, 존재를 감추는 것이 비공개의 뜻이다. 목록(`GET /api/point-types`)에도 담기지 않는다.

**초대는 상태를 최소로 갖는다.** 거절이 없다 — 무시하면 그만이고, 거절 버튼을 두면
「거절함」이라는 상태와 그것을 되돌리는 경로가 따라온다. 은행장의 초대 취소도 없다.
수락하면 초대가 사라지고 회원이 된다. 이미 회원이거나 이미 초대된 사람을 다시 초대하면
같은 초대를 돌려준다(멱등).

**나가기와 내보내기는 같은 일을 하고 누가 정했느냐만 다르다.** 둘 다 **포인트를 회수하지
않는다.** 회원이 아니게 된 사람의 잔액은 그대로 남고, 비공개 은행에서는 보낼 수도 받을
수도 살 수도 없으므로 **쓸 수 없는 채로 남는다.** 이것은 결함이 아니라 설계다 — 잔액을
지우거나 옮기는 코드를 쓰지 않는다. 다시 초대받으면 그대로 되살아난다.

**잔액이 남아 있으면 은행 페이지는 계속 보인다.** 나온 사람도, 내보내진 사람도
`GET /api/point-types/:id` 를 받는다. `404` 는 **존재를 감추는 규칙**이지 회원을 가르는
규칙이 아니고, 잔액 행이 있다는 것은 그 사람이 이미 이 은행과 닿았다는 증거다 — 이미 아는
것을 감추는 것은 감추는 것이 아니라 **고장난 것처럼 보이는 것**이다.

두 곳이 같은 사실을 다르게 말하지 않기 위해서이기도 하다. `GET /api/wallet` 은 그 카드를
통째로 실어 준다. 카드는 보이는데 페이지가 없다고 하면 사용자는 자기가 보고 있는 것이
무엇인지 알 수 없다. **나온 사람에게는 물으러 갈 곳이 필요하다** — 왜 못 쓰는지, 다시
들어가려면 어떻게 하는지가 적힐 자리가 그 페이지다(`docs/JOURNEY.md` 여정 10:
「화면은 그것을 숨기지 않는다」).

보이는 것은 은행의 공개 사실뿐이다 — 이름·발행자·만든 날·상한·유통량. **회원 목록과
초대 도구는 오지 않는다.** 페이지는 「회원이 아니다」와 「그래서 이 잔액을 지금 쓸 수
없다」를 말한다.

**서버가 못 한다고 답한 것을 서버가 해 주면 안 된다.** `Balance.sendable` 이 `0` 인데
`POST /api/transfers` 가 `201` 을 주면, 읽기와 쓰기가 서로 다른 답을 하고 **그 사이로 돈이
실제로 움직인다.** 되돌릴 수 없는 이체에서 이것은 표기 오류가 아니라 사고다. 비공개 은행의
비회원이 보내려 하면 `403 NOT_MEMBER` 다.

받는 쪽에 `RECIPIENT_NOT_FOUND` 를 쓰면서 보내는 쪽에 새 코드를 두는 이유는 **가려야 할
것이 다르기 때문이다.** 받는 쪽에서 감추는 것은 남의 존재고, 보내는 쪽의 사람은 자기가
그 은행에서 나왔다는 것을 이미 안다. 여기서 「대상이 없어요」라고 말하면 감추는 것이
아니라 **엉뚱한 곳을 고치게 만든다** — 사용자는 받는 사람 핸들을 다시 확인하기 시작한다.

**은행장은 나갈 수 없고 내보내질 수도 없다.** 발행할 사람이 없는 은행이 되고, 상한을
바꿀 수도 품목을 관리할 수도 없어진다. `409` 다.

**받는 사람 목록이 좁아진다.** `GET /api/users` 가 `pointTypeId` 를 받는다 — 그 포인트가
비공개면 회원만 담는다. **회원이 아닌 사람에게 보내려 하면 `RECIPIENT_NOT_FOUND` 다.**
새 코드를 만들지 않는 이유는 이 앱의 다른 곳과 같다: 비공개 은행에서 회원이 아닌 사람은
없는 사람과 구별되지 않아야 한다.

동시성 하나 — **마지막 은행장이 나가는 것과 내보내는 것이 겹칠 수 없다.** 은행장 자격을
읽고 지우는 사이에 다른 요청이 끼면 회원이 0 인 은행이 생긴다. 은행 행을 잠그고 센다.

### 아직 계약이 아닌 것

`docs/JOURNEY.md` 의 방향이 앞으로 여기에 더할 것들이다. **아직 확정되지 않았으므로
구현하지 않는다.** 확정되면 더할 것: 게시 품목과 교환권(여정 12·13), 뭉뚱그린 통계,
SDK 용 자격 증명.

`PointType.visibility` 는 창설 시 정해지고 **나중에 바꿀 수 없다.** 공개를 비공개로
바꾸면 이미 받은 사람들이 회원이 아닌 채로 잔액만 남게 되고, 반대로 바꾸면 초대로만
닿던 것이 갑자기 모두에게 열린다. 둘 다 사람에게 일어나는 일이지 설정 변경이 아니다.

**`Transfer.kind` 와 `HistoryEntry.type` 은 다른 것이다.** 앞엣것은 이체냐 발행이냐를,
뒤엣것은 내역 줄의 종류를 가른다.

**이체는 관여한 사람만 읽는다.** `GET /api/transfers/:id` 와 `by-key` 와 목록 전부,
요청자가 보낸 쪽이거나 받은 쪽일 때만 답한다. 남의 것은 **없는 것과 같은 `404`** 다 —
`403` 으로 답하면 "그 id 는 존재한다" 를 알려 주는 셈이고, 이체 id 는 내역에서 새어
나갈 수 있다. `by-key` 는 남의 것이면 `null` 이다(없을 때와 같다).

`GET /api/transfers/by-key` 는 없을 때 `404` 가 아니라 `null` 을 준다.
"안 일어났다" 는 오류가 아니라 정상적인 답이다. 응답을 받지 못한 클라이언트는
이체 id 를 모르므로 id 로는 물을 수 없고, 이것이 유일한 확인 수단이다.

`GET /api/wallet` 은 잔액이 0인 포인트도 **내가 발행자라면** 포함한다. 가졌던 것과
가진 적 없는 것은 다르고, 그 판단은 화면이 한다.

`PointType` 과 `Balance` 는 **요청자 기준으로** 온다. 규칙 판정을 클라이언트가 다시 하지
않게 서버가 결과를 실어 준다 — 같은 규칙이 두 곳에 있으면 곧 한쪽이 틀린다.

| 필드 | 뜻 |
|---|---|
| `PointType.canIssue` | 내가 이 포인트를 발행할 수 있는가 |
| `PointType.issuableHeadroom` | 지금 더 발행할 수 있는 양. **발행자에게만** 뜻이 있다 |
| `PointType.issueCap` | 지금 상한. **보유자에게도 온다** |
| `PointType.totalIssued` | 지금까지 발행된 총량. **보유자에게도 온다** |
| `PointType.nameIsShared` | **원장 전체에서** 이 이름을 쓰는 포인트가 둘 이상인가 |
| `PointType.issuerHandle` | 발행자의 핸들. **유일하다** — `issuerName` 은 흉내낼 수 있다 |
| `PointType.createdAt` | 만들어진 시각. 오래된 것은 흉내낼 수 없다 |
| `PointType.memberCount` | 비공개 은행의 회원 수. 공개면 `null` — 공개 은행에는 회원 개념이 없다 |
| `PointType.visibility` | `"public"` 이면 회원 개념이 없고 누구나 주고받고 산다. `"private"` 는 초대받은 회원끼리만 |
| `Balance.neverSpent` | 이 포인트로 아직 보내지도 사지도 않았다. 공개 은행의 「처음이에요」 표시가 이것으로 켜진다 |
| `Balance.sendable` | 지금 보낼 수 있는 양. 보류금이 생기면 `amount` 와 달라진다 |
| `User.nameIsShared` | **원장 전체에서** 이 이름을 쓰는 사용자가 둘 이상인가 |

**상한은 발행자의 설정이 아니라 보유자에게 하는 약속이다.** 그래서 `issueCap` 은
발행자 여부와 무관하게 온다. 상한과 유통량을 함께 봐야 「앞으로 얼마나 더 풀릴 수
있는가」를 알 수 있고, 그것이 낯선 은행의 포인트를 받을지 판단하는 근거다
(`docs/JOURNEY.md` 여정 10). 상한 변경은 이미 보유자의 내역에 줄로 남는다 — 변경은
보이는데 지금 값은 안 보이면, 사용자는 자기가 본 그 사건의 결과를 확인할 수 없다.

**발행자만 갖는 것은 값이 아니라 바꾸는 힘이다.** `PATCH .../cap` 은 발행자만이고
(`403 NOT_ISSUER`), `canIssue` 와 `issuableHeadroom` 은 발행자에게만 뜻이 있다.
읽는 것과 바꾸는 것을 같은 칸에 두지 않는다.

`nameIsShared` 를 서버가 주는 이유는 `GET /api/users` 가 동명이인을 함께 담는 이유와
같다. **겹친다는 것은 응답의 성질이 아니라 원장의 성질이다.** 클라이언트가 받은 목록
안에서 세면, 겹치는 둘 중 하나만 담긴 응답에서 방어가 조용히 꺼진다.

지갑이 그 경우다. 온포인트가 원장에 둘인데 한쪽만 가진 사용자의 지갑에는 하나만 온다.
클라이언트가 세면 "겹치지 않는다" 가 되어 발행자 부제가 붙지 않고, 그 사용자는 자기가
가진 것이 어느 온포인트인지 확정 화면까지 가도 알 수 없다. 그리고 나중에 다른 온포인트를
받는 순간 같은 카드가 어제와 다르게 보인다.

**겹칠 때 무엇을 보여줄지는 화면이 정한다.** 서버는 겹치는지만 답한다 — 부제를 붙일지,
핸들을 강조할지, 목록에서 인접시킬지는 여정 2·3 의 판단이다.

`PointType` 에는 `issuerName` 도 함께 온다. 이름이 겹치는 포인트를 가르는 부제이고,
화면이 사용자 목록을 뒤져서 발행자 이름을 찾지 않게 서버가 실어 준다.

`GET /api/users?q=` 는 **결과에 동명이인을 무조건 함께 담는다.** 핸들로 검색해
한 명만 맞더라도 같은 이름을 가진 사람을 함께 준다 — 겹친다는 사실은 검색 결과의
성질이 아니라 원장의 성질이고, 클라이언트가 결과 안에서만 세면 `@jisu` 로 검색한
순간 동명이인 방어가 꺼진다.

## 실패

**`GET /api/point-types/:id/members` 는 세 가지로 답한다.**

| 부르는 사람 | 답 |
|---|---|
| 비공개 은행의 회원 | 회원 목록 |
| 비공개 은행의 비회원 | `403 NOT_MEMBER` |
| 공개 은행 | `404 NOT_A_PRIVATE_BANK` |

비회원이 `404` 가 아닌 이유는 **감출 것이 남아 있지 않기 때문이다.** 그 사람은 잔액이
있어 은행 페이지를 이미 본다 — 존재를 아는 사람에게 존재를 감추는 시늉을 하면 감춰지는
것이 아니라 고장난 것으로 읽힌다.

**공개 은행에 빈 배열을 주지 않는다.** 빈 배열은 「지금 회원이 0명」으로 읽히고, 그러면
클라이언트는 늘어나기를 기다리며 다시 묻는다. 공개 은행에 회원 명부가 없는 것은 비어
있는 것이 아니라 **개념이 없는 것**이다. 그리고 `403 NOT_MEMBER` 로 돌려도 안 된다 —
SDK 를 쓰는 쪽은 그것을 보고 「가입하면 되겠구나」로 읽는데, 공개 은행에는 가입이 없다.
**없는 길을 알려 주는 답은 감추는 답보다 나쁘다.**

**없는 경로는 `MALFORMED_REQUEST` 가 아니다.** 본문은 멀쩡하고 경로가 없는 것이라
`UNKNOWN_ENDPOINT` 다. 이름을 틀리면 화면이 「입력을 고쳐 보라」고 말하는데 **고칠 입력이
없다.** 이것은 사용자의 잘못도 데이터의 잘못도 아니고 클라이언트와 서버의 판이 어긋난
것이다 — SDK 를 밖에 여는 이상 흔하게 난다.


오류 응답 본문은 `{ "code": FailureCode, "outcome": "none" | "unknown", "message"?: string }` 이다.
**예외가 없다.** 핸들러가 없는 경로도 이 본문으로 답한다. 프레임워크 기본 404 본문이
새면 `code` 도 `outcome` 도 없고, 클라이언트는 그것을 「결과를 알 수 없다」로 읽는다 —
**아무 일도 일어나지 않은 요청을 두고 돈이 어디 있는지 모른다고 말하게 된다.** 이 앱에서
가장 나쁜 거짓말이고, 없는 엔드포인트를 부르는 동안에만 나므로 구현 중에 제일 자주 난다.

클라이언트는 `code` 로 분기하고 `message` 를 화면에 그대로 뿌리지 않는다 — 화면 문구는
"무엇이 실패했는지 / 돈이 어디 있는지 / 지금 뭘 할 수 있는지"를 담아야 하고, 그건 서버
메시지로 대체되지 않는다.

| 코드 | 상태 | 의미 | 다음 행동 |
|---|---|---|---|
| `INSUFFICIENT_BALANCE` | 422 | 그 포인트의 잔액 부족 | 금액 수정 |
| `CAP_EXCEEDED` | 422 | 발행 상한 초과 | 금액 수정 |
| `NOT_ISSUER` | 403 | 그 포인트의 발행자가 아님 | 없음 (막다른 화면) |
| `ISSUER_CANNOT_LEAVE` | 409 | 은행장은 나가거나 내보내질 수 없음 | 없음 |
| `NOT_MEMBER` | 403 | 비공개 은행의 회원이 아님 | 없음 (막다른 화면) |
| `NOT_A_PRIVATE_BANK` | 404 | 공개 은행이라 회원 명부가 없음 | 없음 |
| `UNKNOWN_ENDPOINT` | 404 | 이 서버에 없는 경로 | 없음 |
| `RECIPIENT_NOT_FOUND` | 404 | 대상 없음 | 대상 다시 고르기 |
| `POINT_TYPE_NOT_FOUND` | 404 | 포인트 없음 | 없음 |
| `SYMBOL_TAKEN` | 409 | 그 기호를 이미 쓰는 포인트가 있음 | 기호 고치기 |
| `MALFORMED_REQUEST` | 400 | 본문이 계약과 다름 | 없음 (화면에서는 도달하지 않는다) |
| `TRANSFER_NOT_FOUND` | 404 | 그 이체가 없거나 내 것이 아님 | 없음 |
| `CAP_BELOW_ISSUED` | 422 | 이미 발행한 양보다 낮은 상한 | 상한 고치기 |
| `SERVER` | 5xx | 서버 오류 | **재시도** (같은 키) |
| `NETWORK` | — | 요청이 서버에 닿지 못함 | **확인하기** → 재시도 |

**결과를 알 수 없는 실패인지는 `outcome` 이 답한다. 코드에서 파생하지 않는다.**

- `outcome: "none"` — 서버가 아무것도 하지 않았다. 확정된 사실이다
- `outcome: "unknown"` — 서버가 처리했는지 서버도 모른다. 드물다(커밋 결과를 못 받은 경우 등)

대부분의 실패는 `none` 이다. 잔액 부족도, 형식 오류도, 없는 대상도 서버는 아무것도 하지
않았음을 안다. 화면은 `none` 일 때 **"아무것도 나가지 않았어요" 라고 단정해도 된다.**

응답 자체가 오지 않는 경우(전송 실패)만 클라이언트가 `unknown` 으로 친다. 서버가 말할 수
없는 유일한 경우이기 때문이다.

**코드에서 파생하지 않는 이유**가 있다. 클라이언트가 "이 코드는 unknown 인가" 표를 들고
있으면 코드를 늘릴 때마다 그 표를 함께 늘려야 하고, 빠뜨리면 **확정된 실패를 「어디까지
갔는지 알 수 없어요」라고 말하게 된다** — 화면이 사용자에게 거짓말을 하는 자리다. 바깥에
SDK 를 열면 그 표를 가진 클라이언트가 우리 것만이 아니게 된다.

`unknown` 일 때만 화면이 단정하지 않는다. 멱등성 키가 있으므로 재시도가 안전하고,
`GET /api/transfers/by-key` 로 실제 상태를 확인할 수도 있다.

`NETWORK` 는 응답이 아니다. MSW 는 `HttpResponse.error()` 로 **전송 자체를 실패**시킨다.
서버가 준 오류와 요청이 닿지 못한 것은 클라이언트에게 전혀 다른 상황이고, 그 차이를
흉내내면 "결과를 알 수 없다"를 검증할 수 없다.

## 동시에 왔을 때

여기부터는 **Mock 이 흉내내지 못하는 계약**이다. MSW 핸들러는 한 프로세스 안에서
요청을 하나씩 처리하므로 아래 상황이 아예 일어나지 않는다. 그래서 Mock 의 구현
모양은 실서버의 참조가 될 수 없다 — 따라 만들면 화면 테스트는 통과하는데 실제
사용자에게서만 깨진다.

아래는 전부 **관측 가능한 계약**이다. 클라이언트가 어떻게 만들어졌는지와 무관하게
지켜져야 한다.

**같은 멱등성 키로 두 요청이 동시에 오면 이체는 하나만 생긴다.** "먼저 조회하고
없으면 만든다" 는 방어가 아니다 — 둘 다 없다고 보고 둘 다 만든다. 키에 unique
제약을 걸고, 위반이 나면 오류가 아니라 **이미 있는 것을 그대로 돌려준다.** 사용자는
응답을 못 받아 다시 누른 것뿐이고, 두 번 빠지면 되돌릴 경로가 없다.

**멱등성 키는 요청자별로 스코프된다.** unique 는 `(요청자, 키)` 복합이지 키 단독이
아니다. 키가 답하는 질문은 "내가 같은 요청을 두 번 보냈나" 이고, 남의 키와 겹치는지는
그 질문과 무관하다. 전역 unique 로 두면 셋이 깨진다 — 남이 내 키를 선점할 수 있고,
선점당한 쪽은 unique 위반 뒤 재조회가 남의 것이라 비어서 **끝없이 재시도한다.** 그리고
"그 키는 이미 쓰였다" 가 남의 활동을 알려 주는 통로가 된다. UUID 라 확률이 낮다는 것은
방어가 아니다 — SDK 를 열면 외부 클라이언트가 순차 번호를 쓸 수도 있다.

**잔액은 읽고 빼서 쓰지 않는다.** 같은 지갑에서 동시에 두 번 나가면 나중 것이 앞의
차감을 덮는다. 조건부 갱신(`balance >= amount` 를 UPDATE 조건에 넣고 영향 행 수로
판정)이나 행 잠금으로 처리하고, 실패하면 `INSUFFICIENT_BALANCE` 다.

**발행 상한도 같다.** 여유를 확인하고 발행하는 두 요청이 겹치면 둘 다 여유가 있다고
보고 상한을 넘는다. 상한 초과는 되돌릴 수 없다 — 이미 발행된 포인트는 남의 지갑에
가 있다.

**refresh 회전이 겹치면 하나만 성공한다.** 클라이언트는 갱신을 한 번에 하나만 돌리지만
그것은 예의이지 보장이 아니다. 탭이 둘이면 동시에 온다. 회전을 원자적으로 처리하고,
진 쪽에는 재사용 탐지를 발동시키지 않는다 — 정상 사용자의 세션이 통째로 죽는다.

**상한 변경도 잠그고 읽어야 한다.** 「이미 발행한 양보다 낮출 수 없다」를 확인하는 동안
발행이 들어오면, 확인은 통과하고 결과는 유통량이 상한을 넘은 상태가 된다. 발행이 상한을
읽을 때와 같은 행을 잠근다.

**기호도 unique 제약이 진짜 방어선이다.** 같은 기호로 두 창설이 동시에 오면 조회는
둘 다 비어 있다고 답한다. 위반이 나면 `409 SYMBOL_TAKEN` 이다 — 여기서는 멱등성 키와
달리 기존 것을 돌려주지 않는다. 남이 만든 포인트를 내 것이라고 답하는 셈이 된다.

**재고와 1인 한도는 잠그고 읽는다** (상점이 붙을 때). 마지막 하나를 둘이 동시에 사면
확인은 둘 다 통과하고 결과는 재고가 음수가 된다. 1인 한도도 같다 — 한도가 둘인데 동시에
셋을 사면 확인이 전부 통과한다. **여기서 틀리면 사용자가 포인트를 잃고 아무것도 못 받는다.**
이 앱에 환불이 없으므로 재고 판정은 되돌릴 수 없는 것의 앞에 서 있는 유일한 방어다.

**핸들은 정규화된 형태에 unique 를 건다.** 조회만 정규화하면 `@Minho` 와 `@minho`
두 행이 동시에 존재할 수 있고, 그러면 어느 쪽이 로그인되는지가 행 순서에 달린다.

## 시뮬레이션

`src/mocks/sim.ts`. 실패하지 않는 앱에서는 정직함을 시험할 수 없다.

```ts
interface SimConfig {
  latencyMs: number        // 기본 400
  jitterMs: number         // 기본 200
  failureRate: number      // 0.0 ~ 1.0. 기본 0
  forceFailure: FailureCode | null   // 다음 한 요청만. 쓰면 소모된다
  loseNextResponse: boolean          // 쓰기를 끝낸 뒤 응답을 버린다
}
```

`forceFailure: 'NETWORK'` 는 요청을 받기 **전에** 실패시키므로 서버는 언제나 아무것도
만들지 않은 상태다. 그것만으로는 멱등성을 시험할 수 없다 — 잔액이 0번에서 1번으로
가는 것을 보는 것뿐이다.

`loseNextResponse` 가 진짜 위험한 경우를 만든다. **서버는 이체를 만들었고 클라이언트는
응답을 받지 못한다.** 이때 같은 키로 재시도해서 잔액이 한 번만 움직이는지가 멱등성의
유일한 실제 검증이다.

## 실기기에서 볼 때

서비스 워커는 **보안 컨텍스트에서만** 등록된다. 폰에서 LAN IP(`http://172.30.x.x:5173`)로
열면 MSW 가 뜨지 않고 모든 요청이 404 가 된다.

```bash
adb reverse tcp:5173 tcp:5173   # 무선 adb 에서도 된다
# 폰에서 http://localhost:5173 으로 연다 — localhost 는 보안 컨텍스트다
```
