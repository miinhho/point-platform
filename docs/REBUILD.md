# 재구축 계획

`JOURNEY.md` 가 무엇을 만들지 정하고, 이 문서는 **어떤 순서로 어떻게** 만들지 정한다.
`PHASES.md` 는 1차 구현의 기록으로 남겨 둔다 — 거기서 배운 것이 여기 반영돼 있다.

## 기술 결정

**상태 — TanStack Query + Jotai**

서버 상태는 TanStack Query, 클라이언트 전역 상태는 Jotai. 둘의 책임이 다르다.

Jotai 비동기 atom 하나로 통일하는 안을 검토했다가 버렸다. 요청 중복 제거, stale-while-revalidate,
재시도, 포커스·재연결 시 재조회, 뮤테이션 수명주기, 키 기반 무효화를 직접 만들어야 하는데
그건 TanStack Query 를 나쁘게 재구현하는 것이다.

| | 담당 |
|---|---|
| TanStack Query | 지갑·사용자·포인트 종류·이체 내역 — 서버가 진실인 것 |
| Jotai | 플로우 상태, 선택된 포인트, 색 모드 — 클라이언트가 진실인 것 |

**Mock — MSW (Mock Service Worker)**

계약을 TypeScript 인터페이스가 아니라 **HTTP** 로 둔다. 1차 구현은 `PointApi` 인터페이스와
로컬 Mock 모듈이었고, 그래서 앱이 HTTP 를 한 번도 쓰지 않은 채 완성됐다 — 멱등성 키가
헤더가 아니라 JS 객체 필드였고, "네트워크 실패"는 로컬에서 던진 예외였다. 실서버를
붙이는 날 클라이언트 계층을 새로 써야 했을 것이다.

지금은 앱이 실제 `fetch` 를 하고 MSW 가 가로챈다. 테스트도 같은 핸들러를 쓴다 —
그래서 테스트가 검증하는 것이 실제 계약(상태 코드·헤더·전송 실패)이 된다.
Spring Boot 가 오면 `src/mocks/` 만 지운다.

주의: 서비스 워커는 보안 컨텍스트에서만 등록된다. 실기기에서는 LAN IP 대신
`adb reverse` 로 `localhost` 를 써야 한다.

**서버 — Kotlin + Spring Boot. 스키마는 Flyway 가 갖는다**

`spring.jpa.hibernate.ddl-auto` 는 **`validate`** 다. `update` 로 두면 스키마의 진실이
엔티티에 있게 되고, 그러면 DB 가 지금 어떤 모양인지 아무도 확정적으로 말할 수 없다.
마이그레이션 파일이 진실이고 엔티티는 그것과 맞는지 검사받는다.

**한 번 나간 마이그레이션은 고치지 않는다. 새 마이그레이션으로 고친다.** 앱에서
확정된 이체를 되돌리지 않고 다음 것을 쌓는 것과 같은 규칙이다. 이미 적용된 파일을
수정하면 체크섬이 어긋나고, 그것을 `repair` 로 습관처럼 우회하면 마이그레이션 이력이
거짓이 된다. Flyway Community 에 되돌리기가 없는 것도 이 앱답다.

회원 자격 · 상점 · SDK 가 얹힐 것이 이미 정해져 있다 — **스키마가 계속 자란다는 것을
아는 상태**에서 도구 없이 가면 그 자람이 전부 추측에 맡겨진다.

**통계 — 지금은 원본에서 읽는다. 분리는 나중이고, 기준은 규모가 아니다**

기준은 **그 숫자가 되돌릴 수 없는 결정에 쓰이는가**다.

- **유통량 · 상한 · 발행 여력** — 발행 결정에 직결되고 발행은 되돌릴 수 없다. **반드시
  원본에서, 잠그고 읽는다.** 지연된 유통량을 보고 발행하면 상한을 넘고, 넘긴 포인트는
  이미 남의 지갑에 있다. 여기는 어떤 사본도 두지 않는다
- **회전율 · 활성 회원 수 · 교환 비율** — 경향을 본다. "어제까지" 로 충분하고 지연돼도
  아무도 손해 보지 않는다. 분리한다면 여기다

그래서 순서는 이렇다. **2 를 건너뛰고 3 으로 가는 것이 흔한 실수다.**

1. 원본에서 집계한다. 인덱스로 충분하다 — 모임 규모의 은행에서 이체는 하루 수백 건이다
2. 느려지면 **같은 DB 에 요약 테이블**을 둔다. 배치나 이벤트로 갱신하고, 원본과 어긋나면
   재계산으로 복구할 수 있게 한다
3. 집계 쿼리가 쓰기 트랜잭션을 기다리게 만들 만큼 커지면 그때 분리한다

분리에는 파이프라인·지연·정합성 검증이라는 상시 비용이 붙는다. 그 비용은 "언젠가 클
것이다" 로 정당화되지 않는다. **그리고 진실이 둘이 되는 것 자체가 이 앱이 계속 피해 온
것이다** — 클라이언트가 서버 규칙을 다시 계산하지 않게 한 것과 같은 이유다.

**문자열 — i18next + react-i18next**

키로 관리하고 타입을 잡는다. RN 셸에서도 같은 카탈로그를 쓸 수 있다.
locale 은 `ko` 하나로 시작하지만 하드코딩을 막는 것이 목적이지 다국어가 목적이 아니다.

**디자인 — Chakra recipe 기반**

`system.ts` 에 토큰과 recipe 를 정의하고 화면은 **토큰 이름만** 쓴다.
`fontSize`·`minHeight`·`bg` 를 화면에서 직접 지정하지 않는 것을 규칙으로 두고 lint 로 잡는다.

## 로그인 시도 제한은 앱이 아니라 앞단에서 (2026-08-19 결정)

**앱에서 뺀다.** `LoginThrottle` 과 `login_failures` 표를 되돌리고(새 마이그레이션으로),
제한은 로드밸런서에서 순수 rate limit 으로 건다.

`/api/auth/login` 에 IP 기준 요청 수 제한 하나면 된다. 성공·실패를 가리지 않는다.

**앱에서 세는 순간 「실패만 센다」와 「성공하면 지운다」가 따라오고, 구멍은 거기서 나왔다** —
성공이 IP 카운터까지 지워서, 자기 계정으로 한 번 로그인하면 그 회선의 기록이 사라졌다.
공격자가 계정 하나만 가지면 IP 제한이 사실상 없었다. 순수 rate limit 에는 `clear` 라는
개념 자체가 없다.

그리고 실패마다 DB 에 upsert 두 번이었다. **방어 장치가 그대로 부하 발생기가 된다.**

### 받아들이는 것 — 계정별로는 세지 않는다

로드밸런서는 본문을 파싱하지 않으므로 **핸들로는 셀 수 없다. IP 로만 센다.** 그래서
IP 를 많이 가진 쪽이 한 계정을 집중해서 찍는 것은 지금 막지 않는다. **모르고 빠뜨리는
것이 아니라 알고 안 하는 것이다.**

그래도 되는 이유는 지금 인증의 수명이다. **회원가입이 없고 계정은 손으로 넣은 여섯 개
뿐이며, Google · Apple 로 갈아탈 것이 이미 정해져 있다**(위 「회원가입은 나중에 한
묶음으로」). 수명이 정해진 임시 인증 위에 분산 공격 방어를 얹는 것은 방어가 대상보다
정교한 것이다.

**소셜 로그인이 설 때 다시 본다.** 그때 암호 로그인이 남는지가 갈리고, 남으면 그때
계정별 카운팅이 필요하다.

### 대신 부팅을 막는다

방어를 앱 밖에 두기로 했으면 **그 방어 없이 운영에 뜨지 못하게 한다.** `ProductionGuard`
가 이미 개발용 기본값을 막고 있으니 같은 자리다 — 앞단 제한이 설정되지 않은 채로는
운영 프로파일에서 서지 않는다. 안 그러면 이 결정은 「나중에 붙이기로 했다」로 남고,
그렇게 남은 것은 붙지 않는다.

**가드는 켜졌다는 것만 안다.** 속성은 `point.login-rate-limited-upstream` 이고, 이것을
`true` 로 두면 서버는 뜬다 — **앞단에 실제로 제한이 걸렸는지는 확인하지 못한다.** 켜기만
하고 로드밸런서를 안 걸면 가드가 거짓말을 하게 된다.

그래도 두는 이유는 **잊는 것과 속이는 것이 다르기** 때문이다. 가드가 막는 것은 잊는
쪽이고, 그쪽이 실제로 일어난다. 대신 배포할 때 확인하는 것을 여기 적어 둔다 —
**`/api/auth/login` 에 요청 수 제한이 실제로 걸렸는지 한 번 쏘아서 확인하고 속성을
켠다.** 순서를 반대로 하지 않는다.

## 주소 (2026-08-19 결정)

화면이 주소를 갖는다. 지금은 전부 `localhost:5173` 하나이고 화면은 Jotai 스택으로만
바뀐다.

**「WebView 라서 주소가 필요 없다」는 틀렸다.** WebView 는 히스토리 API 를 그대로 갖는다.
그리고 이 저장소는 주소가 없어서 이미 값을 치렀다 — `shared/ui/useSystemBack.ts` 가
`history.pushState` 로 **가짜 항목을 덫으로 밀어 넣어** 안드로이드 back 이 앱을 떠나는
것을 막는다. `docs/FIELD.md` R1-1 · R2-1 이 그 라운드다. 덫은 한 겹뿐이라 구조적으로
깨지기 쉽다. 진짜 히스토리가 있으면 시스템 back 은 `history.back()` 이고 몇 겹이든 된다.

### 무엇이 주소를 갖는가 — 장소는 갖고, 진행 중인 일은 갖지 않는다

| 주소 | 화면 |
|---|---|
| `/` | 홈 |
| `/history` | 내역 |
| `/history/{transferId}` | 내역 상세 |
| `/settings` | 설정 |
| `/points/new` | 포인트 만들기 |
| `/points/{pointTypeId}` | 은행 페이지 |
| `/points/{pointTypeId}/members` | 회원 명부 |
| `/points/{pointTypeId}/invite` | 초대 |
| **없음** | 대상 선택 · 금액 · 확정 · 결과 · 실패 |

**이체 흐름에 주소를 주지 않는다.** 그것은 장소가 아니라 진행 중인 일이다. 주소를 주면
새로고침이 무슨 뜻인지 답할 수 없다 — 다시 확정하는 것인가, 처음부터인가. 대상과 금액은
클라이언트가 가진 진실이라 주소에 복원할 것도 없다.

더 나쁜 것은 뒤로 가기다. 확정 화면에 주소가 있으면 **보낸 뒤 뒤로 가기가 「방금 보낸
것을 되돌린다」로 읽힐 여지가 생긴다.** 이 앱은 취소를 의도적으로 없앴다 — 되돌릴 수
없다는 것이 화면에서 흔들리면 안 된다.

**결과 화면에서 뒤로 가면 홈이다.** 흐름은 주소를 바꾸지 않고 홈 위에 뜨고, 끝나면
홈으로 돌아온다. 그 이체를 다시 보고 싶으면 내역에 있고 `/history/{id}` 가 그 주소다 —
**일어난 일은 장소를 갖고, 일어나는 중인 일은 갖지 않는다.**

### 주소는 화면 하나를 가리킨다 — 탭 셋의 스택을 담지 않는다

**주소가 진실이다.** 새로고침하거나 링크로 들어오면 그 주소의 탭이 그 화면으로 열리고,
**나머지 두 탭은 뿌리에서 시작한다.** 탭 스택은 그 세션 안에서만 산다.

주소에 탭 셋의 상태를 함께 싣는 안을 버린 이유는 공유다. 이 앱의 주소는 남에게 보내는
것이고(은행 페이지), 거기에 내 내비게이션 상태가 실리면 **받은 사람이 내가 어디를
거쳐 왔는지를 함께 받는다.** 주소가 장소를 가리키는 것이 아니라 나를 가리키게 된다.

잃는 것은 적다. 내역 깊숙이 들어간 채 홈으로 옮겨 새로고침하면 내역 탭이 뿌리로
돌아가는 정도이고, 되돌아가는 길이 막히지 않는다. 그리고 실제 사용은 WebView 라
새로고침보다 **알림에서 들어오는 딥링크**가 흔한데, 그 경우 다른 탭의 스택은 애초에
없다.

### 로딩·에러 다음이다

주소로 바로 들어오면 그 화면이 첫 화면이 되고, 데이터가 **항상 없는 상태로 시작한다.**
지금은 홈을 거쳐 오니 캐시가 있어서 빈 상태가 잘 드러나지 않았다 — `docs/FIELD.md` R2-1
이 「돌아왔을 때 플레이스홀더가 안 보였다」고 관측한 것이 그것이다. 라우팅을 붙이는
순간 그 상태가 실제로 노출된다.

그래서 순서는 **기다리는 중·실패 화면 먼저, 라우팅 다음**이다. 반대로 하면 딥링크마다
빈 화면이 나오고 그것을 「그 포인트가 없다」로 읽게 된다.

## 회원가입은 나중에 한 묶음으로 (2026-08-19 결정)

지금 로그인은 있고 **회원가입은 없다. 빠뜨린 것이 아니다.** Google · Apple 로그인,
Firebase 연결, FCM 이 함께 와야 하는 일이라 그때 한 번에 한다.

**그래서 지금 「가입이 없다」를 보고 만들지 않는다.** 지금 만들면 핸들·암호 방식으로
한 벌 만들고, 제공자가 붙을 때 그것을 다시 뜯게 된다 — 그 사이에 만들어진 계정의
정체성을 어떻게 옮길지가 새 문제로 남는다.

### 지금 치르는 값

**실서버에 동명이인을 만들 수 없다.** 계정이 손으로 넣은 넷뿐이라 `nameIsShared` 를
실서버에서 확인할 방법이 없다 — 프론트가 실서버 대조에서 이 항목만 판정하지 못했다.
시드에 같은 이름 둘을 넣어 두는 것으로 메운다. **계약을 못 지키는 것이 아니라 못
확인하는 것이므로, 확인하지 못했다는 사실을 그대로 적어 둔다.**

### 그때 반드시 지켜야 하는 것

**제공자가 무엇이든 핸들은 사용자가 고른다.** 핸들은 이 앱에서 유일하고, 사칭 방어의
근거이며(`docs/JOURNEY.md` 여정 10), 「누구에게 보내는가」의 최종 확인 수단이다.
Google 로 들어온 사람에게는 핸들이 없으므로 **가입 흐름에 핸들을 고르는 단계가 반드시
있다.**

**로그인 방법은 셋이다 — 핸들·암호, Google, Apple.** 제공자로 들어오든 아니든 그
다음은 같다.

**추천은 한다. 다만 미리 채워 두지 않는다.** 빈 칸에서 시작하게 하면 사람들은 더 나쁜
핸들을 고르거나 그 자리에서 그만둔다. 그러니 후보 서넛을 보여 주고 **고르거나 직접
쓰게** 한다 — 입력칸에 미리 넣어 두고 「다음」을 누르게 하는 것은 추천이 아니라 자동
생성이다. 그 사람은 자기 핸들을 고른 적이 없고, 그래서 **남이 그것을 흉내낼 때
알아채지 못한다.** 창설의 공개/비공개에 기본값을 두지 않은 것과 같은 판단이다.

추천에는 이 앱만의 조건이 셋 붙는다.

- **이메일에서 뽑지 않는다.** 핸들은 공개되고 이메일은 아니다 — `minho.jang@gmail.com`
  에서 `@minhojang` 을 만들면 핸들이 이메일의 절반을 실어 나른다. Apple 의 가림 주소는
  애초에 뽑을 것이 없다
- **이미 있는 핸들에 숫자만 붙이지 않는다.** 표시 이름이 「온마트」인 사람에게
  `@onmart2` 를 추천하면 **앱이 사칭을 거들게 된다.** 핸들은 이 앱에서 사칭 방어의
  근거다(`docs/JOURNEY.md` 여정 10) — 그 근거를 앱이 흐리면 안 된다
- **추천은 이미 비어 있는 것만 낸다.** 고르자마자 「이미 있어요」가 나오면 추천이 아니다

**추천할 재료가 없어도 흐름이 끝나야 한다.** Apple 은 이름을 첫 인가 때만 주고, 그마저
사용자가 거절할 수 있다. 후보가 0 개인 화면이 정상 경로다.

**계정은 제공자 인증이 끝날 때가 아니라 핸들이 정해질 때 생긴다.** 제공자 인증만으로
행을 만들면 **핸들 없는 계정**이 남는다 — 보낼 수도 없고 찾을 수도 없는데 존재하고,
`createdAt` 은 벌써 시작돼 있다. 도중에 그만둔 사람이 다시 들어오면 그 유령을 만난다.
제공자 신원은 두 단계 사이에 **짧은 수명의 토큰으로 들고 있고 DB 행으로 만들지 않는다.**
그래야 「가입 시점」이 하나로 정해지고, 그만두면 아무것도 남지 않는다.

덤으로 Apple 의 함정 하나를 비껴간다. Apple 은 이름과 이메일을 **첫 인가 때 한 번만**
주고 그다음부터는 안 준다. 우리는 제공자가 준 이름을 쓰지 않으므로 — 이름도 핸들도
사용자가 직접 정하므로 — 그것을 놓쳐도 잃을 것이 없다.

**핸들 중복 확인은 「존재를 알려주지 않는다」의 의도된 예외다.** 로그인은 어느 핸들이
있는지 알려주지 않는다(`docs/API.md`). 그런데 가입에서 핸들을 고르게 하려면 **겹쳤다고
말해야만 한다.** 이 둘은 양립하지 않고, 가입이 생기는 순간 로그인 쪽 규칙의 값은
떨어진다.

그러니 로그인 규칙의 목적을 다시 적어 둔다 — **핸들 목록을 못 얻게 하는 것이 아니라,
암호를 찍어 보는 쪽에 「이 핸들은 있다」는 신호를 주지 않는 것**이다. 가입이 와도
로그인은 계속 두 경우의 문구가 같아야 하고, 방어는 문구가 아니라 **시도 제한**이 한다 —
그 제한은 앞단에 있다(아래 「로그인 시도 제한은 앱이 아니라 앞단에서」). 가입의 중복
확인도 같은 제한 아래 둔다.

**사칭 판단은 가입 시점에 고정된다.** 이미 결정돼 있다 — 「사칭 판단은 계정별로, 가입
시점으로」(커밋 `26a34ec`). 제공자가 여럿이 되어도 이 기준은 하나여야 한다. Google 로
만든 계정과 암호로 만든 계정의 「만든 날」이 다른 뜻이면 그 날짜는 근거가 되지 못한다.

**FCM 이 와도 `watch()` 구독은 돌아오지 않는다.** 알림은 앱 밖에서 부르는 것이지 화면을
실시간으로 갱신하는 장치가 아니다. 되살리지 않는다(`docs/JOURNEY.md` 「버린 것」).

## 폴더 구조

1차 구현은 `ui/` 와 `components/ui/` 가 공존했고 `api/` 안에 순수 로직과 훅이 섞여 있었다.
기준을 하나로 둔다 — **누가 그것을 소유하는가.**

```
src/
  app/          앱 셸. 진입점·프로바이더·색 모드
  domain/       순수 도메인. 프레임워크를 모른다
  api/          HTTP 클라이언트 · 엔드포인트 · 쿼리
  mocks/        MSW. 실서버가 오면 통째로 사라진다
  features/     여정 단위. transfer / wallet / issue / history / settings
  shared/       여러 feature 가 쓰는 것. ui(디자인 시스템) · i18n
  test/         테스트 설정
```

`features/` 는 여정을 따른다. 화면과 그 화면만 쓰는 로직이 같은 폴더에 있어야,
화면을 고칠 때 그 로직이 다른 곳에서도 쓰이는지 찾아다니지 않는다.
`api/recipientList.ts` 가 `features/transfer/` 로 간 것이 그 예다 — API 가 아니라
보내기 플로우의 목록 구성 규칙이었다.

## 작업 단위 — 여정 슬라이스

T0~T2 는 끝났다. **T3(상태) · T4(문자열) · T5(토큰) 은 독립 단계에서 해체했다.**

해체한 이유는 그 순서를 따른 결과가 증명했다.

- 앱을 실행하면 "재구축 중입니다" 한 줄만 나왔다. 다섯 단계 동안 돌아가는 앱이 없었다
- `api/queries.ts` 가 쿼리 6개·뮤테이션 2개를 만들었는데 **호출부가 0개**였다
- T2 커밋이 "쓰이지 않는 export 를 걷어냈다" 고 말하는 동안 T1 이 새로 만들고 있었다
- 테스트가 전부 순수 로직·HTTP 였고 화면 커버리지는 0 이었다 — 이 문서가 1차 구현을
  비판한 바로 그 상태를 재구축이 재생산했다

화면 없이 설계한 상태·토큰·문자열은 맞는지 확인할 방법이 없다. 화면을 붙이는 순간
전부 재작업 대상이 된다. **화면을 두 번 쓰지 않으려고 만든 순서가 화면을 두 번 쓰게
만들고 있었다.**

그래서 상태·문자열·토큰은 **그것을 처음 필요로 하는 화면과 같은 변경 안에서** 태어난다.

| 슬라이스 | 여정 | 화면 | 여기서 처음 세우는 것 |
|---|---|---|---|
| **S0** ✓ | — | (정리) | 죽은 코드 · 주석 규칙 소급 |
| **S1** ✓ | 1 | 홈 — 포인트 카드 목록 | Query 배선 · i18n 부트스트랩 · 토큰 축과 lint 규칙 |
| **S2** ✓ | 2·3·4 | 받는 사람 선택 · 금액 입력 | Jotai 플로우 상태 · 내비게이션 렌더 · 키패드 |
| **S3** ✓ | 5·6 | 확정 · 홀드 · 완료 · 실패 | 멱등성 키 · `useSubmitTransfer` · `failures` |
| **S4** ✓ | 7 | 발행 | `kind` 분기 (상태 기계 재사용) |
| **S5** ✓ | 8 | 내역 · 발행자 화면 · 하단 탭 | `historyQuery` · `ledger` |

S2 와 S3 는 각각 둘이었다(받는 사람 / 금액, 확정 / 결과). 합친 이유는 대상 선택에서 사람을 고르면 갈 곳이
다음 슬라이스에 있어서, 나눠 두면 **갈 곳 없는 버튼**이 생기기 때문이다. S1 에서 카드를
누를 수 없게 둔 것과 같은 판단이다 — 이번에는 나누는 쪽이 그 문제를 만든다.

**S0 을 제외한 모든 슬라이스는 끝났을 때 브라우저에서 만질 수 있다** (`CLAUDE.md` F2).

**S0~S5 전부 완료.** 테스트 181케이스 (도메인·HTTP 계약 96 · 화면 47 · 규율 4 · 나머지 34).
`npm test` · `npx tsc` · `npm run build` 통과. 브라우저 360×780 확인.

두 번 합쳤다. S2+S3(받는 사람+금액), S3+S4(확정+결과). 이유는 같다 — 나누면 갈 곳 없는
버튼이 생긴다. 슬라이스 경계는 "레이어" 가 아니라 **사용자가 끝까지 할 수 있는 일** 이다.

### 슬라이스별 완료 기준

시작 전에 기준을 말하고 시작한다 (F5). 통과를 보이지 못하면 끝난 것이 아니다.

**S0 — 정리** (화면 없음. 유일한 예외) — *완료*
- `api/queries.ts` 에 S1 이 쓰는 것만 남긴다
- 심볼당 2줄 초과 주석 0개. `docs/` 문장 복사는 링크 한 줄로, 회고 서사는 삭제
- 동작 변경 0. `npm test` 그대로 통과

**S1 — 홈**
- 지갑 잔액이 실제 MSW 응답에서 온다. `useState` 사본 없음
- 포인트 카드가 `accent` 로 구분된다. 잔액 0 인 것이 아래로 내려간다
- 화면에 한국어 리터럴 0개
- `fontSize`·`bg` 직접 지정 0개. lint 규칙을 이 슬라이스에서 켠다
- 화면 테스트: 카드가 잔액 순으로 렌더되고 0 잔액이 뒤로 간다
- 브라우저 **360×780** 에서 확인 (실기기 CSS 뷰포트)

**S2 — 받는 사람**
- 홈 카드 탭 한 번으로 진입. 선택된 포인트가 이후 화면에 계속 보인다
- 동명이인 두 명이 인접하고 핸들 대비가 4.5:1 이상
- 자동 포커스 없음 (`FIELD.md` R2)
- 화면 테스트: 동명이인 묶음 · 검색 결과 갱신

- 숫자와 한글이 함께 읽힌다. 13자리에서 360px 폭을 넘지 않는다
- 잔액 초과 시 금액이 붉어지고 확인이 잠긴다 (버튼을 감추지 않는다)
- 잔액 0 카드는 플로우에 들어가지 않는다

**S3 — 확정 · 홀드 · 완료 · 실패**
- 확정 화면에 다섯 항목이 전부 있다 (포인트 이름 · 받는 사람 이름 · 핸들 · 금액 · 보낸 뒤 남는 잔액)
- 확인 다이얼로그 0개. 홀드 600ms, 200ms 에서 떼면 발동하지 않는다
- 멱등성 키는 확정 화면 진입 시 한 번. 두 번 들어가면 2개, 실패 후 재시도하면 1개
- 요청이 나가는 동안 back 이 화면을 바꾸지 않는다
- `NETWORK`·`SERVER` 는 "실패했습니다" 라고 단정하지 않는다
- 응답 유실 후 재시도해도 잔액이 정확히 한 번 빠진다 (테스트로 증명)
- 상태 변화가 `aria-live` 로 읽힌다

**S4 — 발행**
- 발행 문구가 잔액이 아니라 총 유통량을 말한다
- 이체와 발행이 명확히 구분된다

**S5 — 내역 · 발행자**
- 목록 → 상세 morph 에서 이름의 x 가 고정된다
- 표기 한계보다 작은 비율은 `0.01% 미만`

### 작업 규칙

- 슬라이스 하나가 커밋 하나가 아니다. **되돌릴 수 있는 결정 하나가 커밋 하나**다.
  한 슬라이스는 보통 3~6 커밋이 된다
- 호출부와 같은 변경 안에서만 코드를 만든다. 다음 슬라이스가 쓸 것 같아서 미리 만들지 않는다
- 접근성과 화면 테스트를 마지막 슬라이스로 미루지 않는다
- 리뷰는 **슬라이스 시작 전 계획**과 **커밋 단위**로 받는다. 다 구현한 뒤 통째로 받지 않는다

## 살아남는 것

1차 구현에서 검증된 것은 버리지 않는다.

- `domain/points.ts` — 한글 표기 (15케이스). 전역 단위 기호(`P`)만 떼어냈다
- `domain/failures.ts` — 실패를 "돈이 어디 있는지"로 옮기는 것 (7케이스)
- `domain/ledger.ts` — 비율 표기 (6케이스)
- `api/recipientList.ts` — 최근 묶음과 동명이인 인접의 충돌 해결 (8케이스)
- `ui/amountFit.ts` — 자릿수에 따른 글자 크기 (3케이스)
- `ui/useSystemBack.ts` — 히스토리 덫
- `ui/ScreenTransition.tsx` — 방향 있는 전환과 morph 분리
- 멱등성 키 설계 — 재시도가 안전한 유일한 근거

## 사라지는 것

- 취소 창 전부 — `cancelableUntil`, `cancel()`, `NOT_CANCELLABLE`, `cancelled` 상태
- `watch()` 구독 — 서버가 동기로 확정을 돌려주면 필요 없다
- 진행 4단계 — `ProgressStep`, `completedSteps`
- `Transfer.status` — 취소가 없어지자 저장된 이체는 언제나 확정된 것이 되었다.
  시스템이 만들어 낼 수 없는 값을 타입에 두면 화면은 그 상태를 그리게 되고,
  그 화면은 영원히 검증되지 않는다
- `PointApi` 인터페이스 — 계약이 HTTP 로 옮겨갔다
- `screens/Sending.tsx` — 화면 자체가 사라진다
- 쿠폰 (만들지 않았다)

## 부록 — 1차 구현에서 무너져 있던 것

1차 구현은 화면이 돌아가는 데까지 갔지만 아래가 무너져 있었다. 숫자는 실측이다.

| 문제 | 근거 |
|---|---|
| 도메인이 단일 포인트를 타입에 못 박음 | `Account.balance` 하나, `Transfer` 에 화폐 필드 없음 |

| 문자열 하드코딩 | 화면·UI 에 한국어 리터럴 106개 |
| 문체가 번역체 | "아직 아무것도 처리되지 않았다" — 문서 문체가 UI 로 샜다 |

| 죽은 코드 | 아무도 안 쓰는 export 12개 |
| 폴더 분류 없음 | `ui/` 와 `components/ui/` 공존, `api/` 안에 순수 로직과 훅 |
| 주석이 거짓말 | 삭제된 `PRINCIPLES.md` 를 참조하는 주석 12곳 |
| 접근성 | `aria-live` 0개 — 상태 변화가 스크린리더에 안 읽힘 |
