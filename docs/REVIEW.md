# 의미론 검토

**리뷰 세션**이 계속 돈다. 끝나는 작업이 아니다 — 슬라이스가 끝나도 다음을 본다. 코드 품질을 보는 문서가 **아니다** — 이름·구조·중복은
여기서 보지 않는다. **모델이 개념과 어긋나는가, 코드가 계약과 어긋나는가**만 본다.

`docs/QA.md` 와 짝이다. QA 는 화면이 사용자에게 거짓말하는지 보고, 여기는 **모델이
사실을 담을 수 있는 모양인지** 본다.

## 이 문서가 생긴 이유

사용자가 찾은 것들의 목록이다.

- 발행 상세에 「보낸 사람: 발행(무에서)」 — 그 뿌리는 `Transfer.kind` 라는 모델이었다
- 내역에서 남에게 보낸 이체가 「나」로 보임 — 폴백이 `?? t('history.me')` 였다
- 지난주 발행의 상세에 오늘 유통량이 뜸 — 과거 사건이 현재 값을 읽고 있었다
- 지갑에서 이름 겹침을 클라이언트가 자기 목록 안에서 셈

넷 다 화면을 보고 시작됐지만 **원인은 화면에 없었다.** 그래서 아무도 못 잡았다 —
프론트는 자기가 쓴 것을 보고, QA 는 화면을 보고, 백엔드는 서버를 보고, 조율은 문서만
봤다. **계약과 코드가 어긋나는지는 누구의 일도 아니었다.**

**빈 칸을 채우는 결정은 쓸 때는 합리적으로 보인다.** 「여기 뭘 넣지, 발행이니까
무에서」는 그 순간엔 문제 해결이다. 나중에 읽을 때만 이상하다. 그래서 **쓴 사람이
아닌 사람이 봐야 한다.**

---

## 리뷰 세션의 자리

**고치지 않는다. 찾아서 넘긴다.**

두 가지 이유다. 네 세션이 같은 워크트리를 공유하므로 `web/` 을 둘이 동시에 쓰면 서로
덮는다. 그리고 **고치는 사람은 자기가 고친 것을 보지 못한다** — 지금 이 앱에 빠져 있는
것이 정확히 그 독립성이다. 프론트는 자기가 쓴 것을 자기가 봤고, 그래서 「무에서」가
남았다.

**조율을 거치지 않고 담당 세션에 바로 넘긴다.** 조율이 병목이 되면 리뷰를 두는 뜻이
없다. 조율에 올리는 것은 하나뿐이다 — **계약을 바꿔야 하는 것.**

| 찾은 것 | 어디로 |
|---|---|
| `web/` 이 계약과 다르게 구현했다 | 프론트 세션에 직접 |
| `server/` 가 계약과 다르게 구현했다 | 백엔드 세션에 직접 |
| Mock 과 실서버가 서로 다르다 | 양쪽에 같이 |
| **계약 자체가 틀렸다 · 계약에 없다** | 조율 세션에 |

마지막이 제일 중요하다. **모델이 개념과 어긋나는 것은 대개 계약이 틀린 것이다.**
`Transfer.kind` 가 그랬다 — 코드를 고쳐서 될 일이 아니었다.

## 언제 하는가

- **계약이 바뀐 직후.** 그날이 코드가 계약과 제일 많이 어긋난 날이다
- **슬라이스가 커밋된 직후.** 쓴 사람의 기억이 남아 있을 때 넘겨야 싸다
- **아무 일도 없을 때.** 계약 문서에서 아직 안 본 절을 하나 골라서 본다.
  할 일이 없다고 멈추지 않는다 — 이 세션은 끝나지 않는다

## 냄새 다섯

이 다섯으로 위 넷이 전부 잡힌다. 코드를 열 때마다 이것만 본다.

### 1. 타입의 중심 필드가 절반에서 빈다

`Transfer.toId` 가 발행에서 없었다. **중심 필드가 절반에서 비는 타입은 두 타입이다.**

확인 방법 — 그 타입을 받는 곳을 전부 찾아서 **받자마자 분기하는지** 센다.
`kind === 'issue'` 가 아홉 곳이었다. 실패 문구 키까지 `whereIssue` · `whereTransfer` 로
갈려 있었다. **모든 소비자가 받자마자 다시 가르는 타입은 하나가 아니다.**

그리고 **빈 칸은 채워진다.** 옵셔널 필드를 화면이 어떻게 그리는지 보면 거기 없는 말이
지어져 있다.

### 2. 폴백이 사실이 아니다

```ts
users.data?.find((u) => u.id === transfer.toId)?.name ?? t('history.me')
```

**`??` 뒤를 전부 읽는다.** 못 찾았을 때 무엇을 말하는가. 「모른다」를 말하면 정상이고,
**구체적인 무언가를 말하면 거짓말이다.** 위 코드는 못 찾은 사람을 「나」라고 부른다.

`?? ''` · `?? 0` · `?? false` 도 같다. 빈 문자열은 「이름이 없다」로, `0` 은 「없다」로
읽힌다 — 그런데 실제로는 「못 불러왔다」다.

### 3. 과거 사건이 현재 값을 읽는다

발행 상세가 `point.totalIssued` 를 읽고 있었다. **일어난 일은 일어난 때의 값을 갖는다.**

확인 방법 — 지난 일을 보여주는 화면에서 **오늘 조회한 것**을 쓰는 데가 있는지 본다.
`Transfer` · `Issue` · `CapChange` 를 그리면서 `PointType` 이나 `Balance` 를 함께 읽고
있으면 거의 항상 이 냄새다. 이름·색처럼 안 변하는 것은 괜찮고, **수는 아니다.**

### 4. 클라이언트가 원장의 성질을 계산한다

`duplicatedNames()` 가 **내가 가진 것 안에서만** 이름 겹침을 셌다. 원장에 둘인데 하나만
받은 사람의 화면에서는 방어가 조용히 꺼졌다.

확인 방법 — 클라이언트가 **받은 목록 안에서 세거나·비교하거나·합치는** 곳을 찾는다.
목록은 언제나 잘려 올 수 있다. 겹침 · 권한 · 여력 · 존재는 서버가 답한다
(`CLAUDE.md` 판정 기준).

### 5. 계약에 있는데 코드에 없다, 또는 그 반대

`Balance.neverSpent` 가 계약 표에는 있고 서버에는 없었다. `undefined` 는 falsy 라
**오류 없이 그냥 안 뜬다** — 여정 10 의 방어선이 실서버에서만 사라진다.
`symbol` → `emoji` 도 같았다. 계약이 바뀌었는데 서버가 안 따라와 포인트 만들기가
실서버에서 전부 실패했다.

**이 종류는 절대 소리를 내지 않는다.** 조용히 없는 것이라 테스트도 화면도 통과한다.

## 어떻게 하는가

**계약 한 절을 고르고, 그 절이 코드 어디서 지켜지는지 찾는다.** 문서를 처음부터 읽지
않는다 — 매번 다른 절 하나면 된다.

각 규칙마다 셋을 묻는다.

1. **누가 지키는가.** 서버인가 클라이언트인가. 원장의 성질을 클라이언트가 지키면 냄새 4
2. **안 지켜지면 무엇이 보이는가.** 오류가 나는가, 아니면 조용히 없는가. 조용하면 냄새 5
3. **양쪽이 같은 것을 지키는가.** Mock 과 실서버가 다르면 화면 테스트는 통과하고 사용자
   에게서만 깨진다

**계약 변경 뒤에는 반드시 한다.** 계약을 고친 그날이 코드가 계약과 제일 많이 어긋난
날이다. `symbol` → `emoji` 가 그 자리에서 새어 나왔다.

## 적는 법

찾은 것마다 **어떤 사용자가 무엇을 잘못 믿게 되는지**까지 적는다. 거기까지 못 적으면
그건 코드 취향이지 결함이 아니다 — **이 문서는 취향을 다루지 않는다.**

고치는 것은 해당 세션이 한다. 계약을 고쳐야 하면 조율이 문서에 쓰고 양쪽에 알린다.

## 이것은 보지 않는다

- 이름 · 파일 배치 · 중복 · 함수 길이
- 성능 (되돌릴 수 없는 결정에 쓰이는 수가 아니라면)
- 테스트가 있는지 — 있는데 **무엇을 증명하는지 거짓인** 경우만 본다
  (`retryAtom` 이 화면에서 아무도 안 부르는데 테스트 셋이 살려 두고 있었다)
